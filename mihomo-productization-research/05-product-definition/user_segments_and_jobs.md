# WP-4 用户场景、需求与功能价值分析

- 研究日期：2026-10-28
- 输入：WP-1 行为目录（SRC-451）、WP-3 竞品矩阵/生态图谱/社区问题样本（SRC-452/453）、WP-10 客户端内核矩阵（SRC-454）、WP-1 依赖清单（SRC-456）、风险登记（SRC-455）
- 配套文件：`feature_inventory.csv`、`feature_value_risk_matrix.csv`

## 0. 证据方法与代表性限制（先读）

本项目**没有做过任何真实用户研究**：无问卷、无访谈、无遥测。本文件全部需求判断来自三类二手材料——

1. **同类项目 issue 样本**（WP-3 归并）：MyClash 近期 issue 约 10 条定性样本、数据层三项目各数条。样本量小、偏向「出了问题才发声」的人群，且 MyClash 维护者当日清零使可见样本系统性偏低（SRC-452 偏差声明）。**这些样本只能证明「某类问题存在」，不能证明其在用户群中的占比。**
2. **客户端/内核源码事实**（WP-10，E3 级）：关于接管、合并、失败模式的陈述是源码级事实，可靠；但「用户会不会因此困惑」仍属推论。
3. **项目维护者本人的使用记录**（E1，单一样本）：维护者是重度用户（双设备、多机场、金融/AI/隐私全需求），其偏好**恰是本文件要警惕的替代偏差来源**——凡仅有此来源支撑的判断，均在文中标「单一样本」。

因此本文件出现的「高频/刚需」一律指「在可见样本与生态共性中反复出现」，不指统计意义上的多数。凡证据不足处标 **** 并在 §10 汇总验证方式。

## 1. 新手桌面用户

- **要完成的任务**：导入订阅+脚本后「能科学上网、国内直连、视频不卡」，不理解也不想理解分流原理。
- **当前常见配置方式**：照教程复制脚本地址→默认参数全开→出问题先换节点、再换机场、最后发 issue 求助。MyClash #64「FlClash 怎么配置呀」即此类（E1，SRC-452）——新客户端上手求助是 issue 流的固定成分，尽管样本只有一条，它与每个脚本项目都存在的「README 驱动上手」形态互相印证。
- **典型失败模式**：
1. 导入即脚本解析错误（MyClash #65 QuickJS 私有名语法，E2）——阻断型故障，新手无自救能力；
2. 规则集/DNS 冷启动失败时全网不通，且报错信息不指向脚本层；
3. 开关语义误读后「改了没效果」：如把「过滤倍率」当「显示倍率」用（F-21/26 语义对，见 feature 矩阵），或以为「IPv6 总开关」关掉了全部 IPv6（F-33 实际只控制 dns.ipv6，WP-1 明示为命名缺口）。
- **易误解选项**：F-33 IPv6 总开关（命名过度承诺）、F-21/22 显示 vs F-26/27 过滤、F-31/32 双 IP 优先互抵、F-30 屏蔽 QUIC 附带门控规则集而不自知。
- **对默认/透明度/资源的要求**：默认即最优是唯一可接受形态；组数量本身即认知成本（Go 主版默认生成约 37 组，WP-1 实验计数）——新手不要求少功能，要求**默认呈现收敛**（地区组+少数服务组可见，其余折叠/按需开）。资源占用要求低敏感，前提是首启不卡死。
- **需要的文档/诊断/恢复**：一页式上手（导入→验证三步）；「导入后自检清单」（节点数、各组非空、DNS 通）；一键回退到上一个可用配置的说明。当前生态无任何一家提供脚本层自检输出，此为可防御的差异化点。

## 2. Bettbox 用户

- **要完成的任务**：在 Bettbox 的 GUI 里用可视开关管理分流（这是生态中唯一把脚本开关做成 GUI 的客户端，SRC-301/303），双设备/多订阅各一份配置。
- **当前常见配置方式**：脚本声明 `Compatible_With_Bettbox` + `ruleOptionsEnable`，GUI 选择以 `Object.assign` 回注脚本全局变量后执行（WP-10，E3）。用户的开关表整表存储于客户端配置。
- **典型失败模式**（均为 WP-10/WP-1 源码事实，非推测）：
1. **开关整表替换陷阱**：GUI 传入的开关表若缺键，脚本侧三处门禁已加固为「缺失=开」（分流组类），但默认关型开关（过滤/屏蔽类）缺失=关——用户在 GUI 里「没动过」的开关，其实际值取决于脚本侧的缺失语义分类，用户无从知晓（行为目录 §3）；
2. **非布尔强制 true**：开关值非布尔时客户端强制转 true（scripts.dart:49，E3）——配置损坏的表现是功能被打开而非报错；
3. **App patch 覆盖**：general 段由 App 覆盖脚本；sniffer 在 App 开启覆写时被整体替换，F-35 在此客户端下静默失效（E3）；
4. **沙盒上限**：evaluate 10s/128MB——大订阅+全组生成时存在超时风险（机制事实；实际触发频率无样本）。
- **易误解选项**：凡被 App 接管的字段（general/sniffer），脚本开关的存在会制造「已设置」的错觉；DNS 例外地由脚本赢（overrideDns 默认 false），与其他字段的直觉相反。
- **要求**：对该人群，透明度要求具体化为一条：**脚本必须能声明「本开关在当前客户端是否有效」**，或至少在文档中给出分客户端的开关有效性表（WP-10 矩阵已提供原料）。可控性要求已由 GUI 满足，是八类场景中最高的。
- **核心/可选指向**：服务组全集对此人群是核心卖点（GUI 开关的产品形态本身）；F-35、F-33 应标注客户端前提。

## 3. Clash Verge Rev 用户

- **要完成的任务**：把同一套分流逻辑用到 CVR 的订阅覆写链（Merge/Script）上，或干脆只借用规则与分组结构。
- **当前常见配置方式**：Script 覆写入口 `main(config)` 约定与 Bettbox 相同，但引擎为 Boa、执行前键名统一小写、无 GUI 开关回注——改开关须直接编辑脚本或配合 Merge 文件（WP-10，E3）。
- **典型失败模式**：
1. **静默失效（fail-open）**：脚本异常/超时（5s）时 CVR 记录日志并**原样返回输入配置**——用户的表现是「脚本像没装一样」，分组/DNS 全非预期且无报错弹窗（E3）。这是 CVR 场景的第一失败模式，与 Bettbox 的「报错/被覆盖」性质完全不同；
2. 键名小写化与脚本内大小写敏感逻辑冲突的风险（机制事实，未实测）；
3. 脚本引用的 `ruleOptionsEnable` 在 CVR 无 GUI 承载，用户直接面对 36 个开关的原始对象。
- **易误解选项**：全部 36 个——没有 GUI 分层时，开关呈现成本由文档承担。
- **要求**：对此人群，默认值即文档：需要一份「CVR 专用最小改动指南」（只列需要手改的 3–5 个开关）。多订阅覆写链顺序（全局脚本 vs 单订阅脚本）需在文档中明确，否则同一脚本在不同订阅上行为不一致会被报为 bug。
- **核心/可选指向**：核心逻辑须与 Bettbox 版**逐项一致**（同一脚本双客户端是本谱系既有事实），差异只允许出现在交付说明层。

## 4. 软路由 / 裸 Mihomo 用户

- **要完成的任务**：在路由器或服务器上以单一 YAML 运行 mihomo，全家/全屋共用；或用 OpenClash 管理。
- **当前常见配置方式**：裸 Mihomo 无覆写层——脚本产物必须以「生成好的完整 YAML」形态交付，或由用户在外部运行 JS 后取结果；OpenClash 的覆写体系是 INI 模块+Shell 脚本，**JS main(config) 完全不可复用**（WP-10，E3）。该生态的主流现成方案是 COCR 式模板+proxy-providers（SRC-453）。
- **典型失败模式**：
1. **启动即失败**：`empty-fallback` 填策略组名在官方主线 v1.19.33 parser 中直接返回解析错误（R-010，WP-2 源码证据）——脚本默认参数（groupBaseOption 家族）在 Bettbox 实机正常、搬到官方内核即阻断启动。这是本场景证据等级最高、后果最重的一条；
2. proxy-providers 型订阅与脚本「含 proxy-providers 即抛错」的输入契约冲突（行为目录 §1）——软路由生态恰恰以 providers 为主流形态；
3. 路由器 CPU/内存约束下，规则集总量与组数量的成本被放大（WP-11 承接量化）。
- **易误解选项**：「脚本支持软路由」的笼统宣称——实际分三档：裸 mihomo（需产物形态改造+内核语义核对）、OpenClash（需另做覆写模块）、其他 LuCI 插件（未调查）。
- **要求**：此人群对透明度要求最高（配置即全部界面）、对 GUI 零要求、对**可复现与可版本管理**要求最高（配置进 git 是常见实践，属生态观察 E1）。资源占用要求为八类中最硬：路由器内存以百 MB 计。
- **核心/可选指向**：若产品化要覆盖此场景，轻量版的天然定义即在此（组数/规则集/外部请求三项可测量上限，交 WP-5）；在未解决 R-010 与产物形态前，不应宣称支持。

## 5. 多平台 / 多设备用户

- **要完成的任务**：手机、桌面、（可能）路由器共用一套分流意图，各端只改节点选择。
- **当前常见配置方式**：同一脚本多端导入；组内选择靠各客户端本地记忆，脚本以 `profile.store-selected/store-fake-ip` 固定写入保证客户端保存选择（行为目录 §4）。
- **典型失败模式**：
1. 各端客户端接管边界不同（§2/§3/§4），「同一脚本」实际行为三端三样，且差异点恰在用户最在意的 DNS 与连接面（R-008）；
2. Smart 线：学习数据随重导清空、组内显示退化（项目历史记录，单一样本，E1）——多设备频繁重导者最先撞上；
3. 自有图标等资产托管于脚本仓同一地址，仓库可见性变更会同时打断所有设备（R-004）。
- **易误解选项**：「跨端一致」的预期本身——需要在文档层把「一致的是分流意图、不一致的是客户端接管部分」讲明。
- **要求**：默认值跨端一致 > 单端最优；升级脚本时选择记忆不丢失（store-selected 已覆盖）；对资源占用无统一要求（按最弱端计）。
- **核心/可选指向**：跨端一致性测试应进 WP-14 矩阵；combo 式个人专属逻辑（单设备双池隔离）与此人群无涉，属维护者个人形态，不入产品定义。

## 6. 金融 / AI / 媒体 / 开发工具分流需求用户

- **要完成的任务**：让特定服务走「对的出口」——AI 服务走支持地区节点、金融走低风控出口、开发工具（GitHub）稳定、媒体走大带宽/低倍率节点。各子需求的共同结构是**服务×地区×节点质量的三维匹配**，而非单纯分流。
- **当前常见配置方式**：依赖脚本预置的服务组+默认选中地区；不合用时以 issue 要求改默认归属。MyClash issue 中此类占可见样本的显著部分：Epic 直连争议直接引发上游改码（#63，E2）、Gemini 归属致地区错误（#52，E2）、HuggingFace 与 AI 组节点成本冲突（#60，E1）、Patreon 风控封号后求独立分组（#51，E1）（SRC-452）。
- **典型失败模式**：
1. 新服务/新域名未被分类覆盖，直落默认组触发地区限制（官方源 #184 openai 遗漏，E2；Loyalsoldier #504 Apple Intelligence 同型，E2）——分类时效是全生态共同缺口；
2. 默认归属与个人节点结构冲突（如 AI 组默认地区无可用节点）；
3. 金融类走错出口的后果不是「慢」而是风控/封号（#51 报告者自述，E1）——故障影响分级在此人群显著高于其他场景。
- **易误解选项**：以为分组是纯粹的域名清单问题——实际默认选中地区（组级策略）同样决定成败；F-29「分流组添加所有节点」会拆掉地区优选、与此类需求正相反。
- **要求**：需要的是**低成本单服务改道**（把某域名/服务挪到另一组）与**分类清单可对账**（AI 手写补缺口清单资产化，WP-3 机会 5）。对默认行为的要求是保守：风控敏感组（Financial/Cloudflare）默认策略宁可慢、不可错。
- **核心/可选指向**：AI（F-07）+Claude（F-09）为核心差异化；Financial（F-18）专业但默认应开（关掉的代价不对称）；其余媒体/社媒组为可选默认开。

## 7. 熟悉 Clash/Mihomo 的高级用户

- **要完成的任务**：把脚本当框架用——改默认、加自定义组/规则、接自建节点与自建服务（Emby),并预期自己的改动不被脚本覆盖。
- **当前常见配置方式**：fork/自存脚本改源码；或用脚本预留的自定义组能力（buildCustomizeGroups）；自建节点含未知字段与 dialer-proxy 链式引用。
- **典型失败模式**：
1. 上游/脚本升级覆盖自改（本项目用户自身的历史教训即整推覆盖事故，项目记录）——产品形态上对应「发布物与用户改动如何共存」问题；
2. 节点未知字段被重建丢弃——本项目已验证为展开复制保留（WP-1 §4，E2），此点是可写进文档的信任承诺；
3. 识别正则对自建命名（机房/中转/家宽标注）的误判与误删（F-28/F-26），且被过滤清单不可见、难自查。
- **易误解选项**：开关门禁的两类语义（缺失=开 vs 缺失=关）——高级用户直接读写 ruleOptionsEnable 时同样会踩（行为目录 §3）。
- **要求**：透明度要求最高且具体：字段覆盖策略表（哪类字段脚本全权/补默认/不碰）应成为公开文档的一等公民——本项目「读现有值、缺失才补默认」哲学（仅 Go 线，WP-1 §4）正是此人群的核心购买理由，应显性产品化而非只写在代码注释里。可控性要求：扩展点稳定（自定义组、hosts 合并、nameserver-policy 合并均已是合并语义，E2）。
- **核心/可选指向**：F-16 Emby、F-35 Sniffer、F-36 STUN、链式修复（非开关，恒开）对此人群是留存级功能；其余人群眼中的长尾在此是核心。

## 8. 希望尽量少改动客户端原有配置的用户

- **要完成的任务**：只借脚本的分流能力，连接面（端口/LAN/模式/日志/TUN/DNS 客户端侧设置）保持自己在客户端里调好的样子。
- **当前常见配置方式**：在上游谱系中此需求**无解**——上游 main() 以空对象从零构建、连接面无条件赋默认值（WP-1 §4 对照，E2）；本项目 Go 线以 `=== undefined` 逐项判定「缺失才补默认」正面回应了它，custom 线不具备。
- **典型失败模式**：
1. 用错线（custom 线）导致客户端设置被静默重置，且用户归因于客户端 bug;
2. 顶层 ipv6 的条件写入缺口：App 已设 true 时脚本的 WebRTC 防护第三件不生效（行为目录 §3）——「少改动」与「防护全开」在此存在已知张力；
3. 端口类字段的故意不补（socks/redir/tproxy 缺失=不启用）对依赖这些端口的用户是隐性行为差异（注释明示，但文档层未必触达）。
- **易误解选项**：以为两条线的差异只是功能多少——实际是配置哲学差异，应在命名/文档上可区分。
- **要求**：这是唯一把「不做什么」当核心价值的人群：要求脚本公开承诺不碰的字段清单（external-controller/secret 已明确不写，可入承诺）。默认行为要求：除分流面外零副作用。
- **核心/可选指向**：对此人群，轻量/全量的区别不重要，「Go 线哲学」本身就是产品；发布时应把覆盖策略表作为卖点文档（与 §7 共用同一资产）。

## 9. 跨场景共性结论

1. **默认值的分量被 issue 样本一致放大**：归属争议、识别误判、静默失效三类问题全部发生在默认路径上；高级设置的存在感远低于默认值正确性。产品优先级应为：默认归属清单维护 > 单服务改道机制 > 新增服务组 > 新增开关。
2. **静默失效是全生态共同的信任杀手，且每客户端形态不同**：Bettbox 是「被覆盖」，CVR 是「fail-open 装作没装」，官方内核是「解析报错启动失败」，规则层是「0 字节/误杀静默生效」。任何「已生效」宣称都必须附该客户端的验证方式（与 WP-10/WP-14 对接）。
3. **开关数量已不是主要矛盾，开关语义才是**：36 个开关中，误解集中在 6 个（F-21/26 对、F-31/32 对、F-33、F-30）——全部是命名/语义问题而非功能问题，修复成本远低于新增功能（详见 feature 矩阵的合并/改名建议）。
4. **资源占用的硬约束只在软路由场景成立**，其余场景的「轻量」诉求实为认知负荷（组数）而非性能；轻量版定义因此应双轨：呈现轻量（组数/默认可见集）与资源轻量（规则集/请求数上限），交 WP-5 决策。

## 10. 证据最薄弱的假设清单（须后续验证，禁止直接用于决策）

| 编号 | 假设 | 当前证据 | 验证方式 |
|---|---|---|---|
| H-1 | 新手失败后先归因机场，脚本自检可降低支持成本 | 无（推论） | 发布后对 issue 按根因归类统计 3 个月 |
