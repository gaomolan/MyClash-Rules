# WP-5 轻量版与全量版边界研究

- 研究日期：2026-10-28
- 性质：方案研究与决策建议；不改任何仓库代码（章程 WP-5 边界）
- 输入：WP-4 功能价值矩阵与场景分析（SRC-461/462）、WP-1 行为目录与变体矩阵（SRC-463/464）、WP-3 竞品矩阵（SRC-465）、WP-11 性能实测（SRC-466）、WP-10 客户端兼容事实（SRC-467）、风险登记 R-003/R-010（SRC-468）、WP-5 隔离实测（SRC-469）
- 方法声明：WP-4 的归属建议在本文件是**输入而非结论**。凡与 WP-4 不一致处，均在 §4 与 §8 显式列为分歧并给出依据；凡接受处标注接受理由，不以转述冒充复核。

## 0. 结论先行

1. **「轻量」应定义为双轨可测量指标**：呈现轨（可见组数、需理解开关数）+ 资源轨（规则集数、首启下载量、外部依赖构成）。生成耗时与脚本体积经 WP-11 实测**证伪为杠杆**，不入定义、只设回归护栏（§1）。
2. **推荐方案 B（共享核心 + 功能清单构建生成）为目标形态，方案 C/E（单脚本 + 档位预设）为阶段 1 过渡**。B 是唯一能结构性消除 R-003 漂移、且产物仍为单文件（与 Bettbox QuickJS / CVR Boa 沙盒形态完全兼容）的路线；C 先行落地可让归属表与轻量定义立即生效，不必等构建链（§2）。
3. **与 WP-4 共有 4 处分歧**：Financial 轻量默认开（建议改关）、AdBlock 的附条件核心（建议把条件硬化为上线门禁）、F-31/32 三态合并（建议推迟至 GUI 承载验证后）、F-33 改名路线（建议明确选改名而非悬置二选一）。另有 2 处加注接受（F-29 弃用执行路径、倍率族只合并呈现不合并存储键）（§4/§8）。
4. **双档足够，不建议第三档**：「极简地板」已实测备查（§1.3），但第三档使发布矩阵与测试矩阵再翻一档，与防漂移目标背反；是否增设列为所有者拍板项（§7）。

### 1.2 候选维度判定

| 维度 | 是否入定义 | 判定依据 |
|---|---|---|
| 代理组数（可见组数） | **入（呈现轨主指标）** | WP-4 §1/§9.4：新手的「轻量」诉求实为认知负荷，组数是其直接载体；且组数随开关档实测可变（45→40→37） |
| 规则集数 | **入（资源轨主指标）** | WP-11 结论原文：「轻量版的可测量杠杆在规则集数与首启下载量」；规则集数是冷启动请求数与运行时规则规模的共同上游变量 |
| 首启下载量 | **入（资源轨主指标）** | 同上；以 rules-canary 巡检顺带记录体积趋势可低成本持续监测（WP-11 §5 已建议） |
| 外部依赖数 | **入（资源轨副指标，按构成计权）** | 单纯计数意义弱（38 集同属一个源与分属八个源风险完全不同）；改为「宿主数 + 个人源个数」双计数。轻量档剔除 666OS/emos 两个个人源（随 F-16 默认关）的质量收益大于数量收益 |
| 用户需理解的开关数 | **入（呈现轨副指标）** | WP-4 §9.3：误解集中在 6 个开关的语义而非数量本身；但呈现面（GUI 列表长度、文档解释篇幅）仍是可测量的认知成本，以「需文档逐项解释的开关数」计数 |
| 生成耗时 | **不入（仅护栏）** | WP-11 实测证伪：千节点 ≤25 ms，相对冷启动（约 0.9 MB 下载+内核加载）可忽略；客户端引擎即便慢 5–20 倍（WP-11 量级推测）仍在亚秒级。护栏值：合成 1000 节点生成 ≤100 ms（V8 口径），超限视为回归而非版本属性 |
| 脚本体积 / 输出 JSON 体积 | **不入** | gzip 后 14–24 KB 量级，两版差异无用户可感知影响（WP-11 §8）；输出 JSON 差异（实测 -11%~-18%）同理 |
| 节点规模适应性 | **不入** | WP-11 §8：现实区间（≤1000 节点）内不构成任何版本的性能约束，不按节点数分版 |

### 1.4 推荐定义（双轨，对应 WP-4 §9.4 的双轨建议，予以采纳并定额）

在标准夹具（6 地区、倍率标记与信息节点构成同 WP-5 实验）与默认开关档下，**轻量版须同时满足**：

| 轨 | 指标 | 轻量版定额 | 全量基线 |
|---|---|---|---|
| 呈现轨 | 可见代理组数 | ≤ 26 | 30 |
| 呈现轨 | 需文档逐项解释的开关数 | ≤ 20（全量 36 中，轻量只呈现其归属子集） | 36 |
| 资源轨 | 规则集数 | ≤ 33 | 38 |
| 资源轨 | 首启规则集下载量 | ≤ 800 KiB（巡检口径，逐集实测后修订） | ≈876 KiB |
| 资源轨 | 规则集宿主数 / 个人源数 | ≤ 3 / ≤ 1（仅允许 AWAvenue 一类有公开仓库与版本记录者，个人双源为 0） | 4 / 3 |
| 护栏（非定义） | 1000 节点生成耗时（V8 口径） | ≤ 100 ms | ≤25 ms 实测 |

说明：定额取 B 档实测值并留小幅余量，目的是让「轻量」成为**可回归断言**而非营销词；任一指标超限即视为轻量版缺陷，与全量版缺陷同级处理。软路由场景的资源硬约束（WP-4 §4）在此定义下只是被部分覆盖——路由器内存以百 MB 计的运行时占用不在脚本侧可测范围（WP-11 §6.2），轻量定义不承诺运行时内存指标，见 §7 拍板项 8。

## 2. 方案比较

### 2.0 共同前提：产物形态与引擎事实

两个目标客户端对脚本的承载形态一致——**单文件 JS、入口 `main(config)`**，这是不可谈判的产物约束（WP-10，SRC-467）：

- **Bettbox（QuickJS/rquickjs）**：先以 `extract_options`（限额 2 s / 32 MB / 栈 512 KB）只跑脚本顶层，提取 `ruleOptionsEnable`、`serviceConfigs`、`Compatible_With_Bettbox.policyGroupOptions`；再以 `evaluate`（10 s / 128 MB）在调用 `main()` 前用 `Object.assign` 回注 GUI 开关选择。推论：**任何方案的产物都必须保持开关表与服务定义为顶层静态字面量**；构建期拼接不得把它们变成运行时计算结果，否则提取阶段直接失败。
- **Clash Verge Rev（Boa）**：超时 5 s、配置 JSON 上限 10 MB、执行前键名统一小写、无 GUI 开关回注；失败语义为 fail-open（异常即原样返回输入配置，用户无感知）。推论：产物错误在 CVR 上是**静默失效**，方案越依赖复杂构建裁剪，错误越难见——这是 §2.5 不选 D 的关键理由。
- 两版产物在两台引擎上的性能余量都极大（生成 ≤25 ms vs 限额 5–10 s，相差两个数量级以上），**引擎适配性不构成方案间的区分项，产物形态合规才构成**。

### 2.1 方案 A：两份独立脚本

- 形态：lite 与 full 各一份手写单文件（MyClash 现行精简 42 KB / 全量 53 KB、18 / 36 开关即此模式；SRC-465）。
- 优点：各自独立演进、单版故障不波及另一版；用户拿到的是「所见即所得」的单一文件；与客户端覆写形态零摩擦。
- 缺点：**漂移是该模式的常态而非风险**——上游双脚本靠人工同步，本项目三件套人工派生（Go→smart diff 58 行、Go→combo diff 144 行）已是 A 的变体，R-003 评级为高（4×3）；再加轻量维度后发布文件变为 4 个（Go/Go-smart × lite/full），人工同步面翻倍，而 combo 仍需第五次派生。
- 测试成本：每版全量回归；共享行为靠人肉对照，无结构性保证。
- 与现行流程衔接：即现行流程本身，无迁移成本——但等于宣布 R-003 长期不可解。

### 2.2 方案 B：共享核心 + 两份功能清单构建生成

- 形态：源码拆为「共享核心」（节点管线、DNS、组骨架、门禁语义）+「功能模块」（按 serviceConfigs 式数据表组织）+ 两份功能清单（lite 清单 / full 清单）；一个 Node 构建脚本拼装出两个单文件产物。HiClash 的 `Script/shared` 单源块 + `sync-shared.js` 同步 + 漂移检查是本方案在生态内的**已验证弱化版**（SRC-465），证明块级单源+同步脚本+golden 的组合在本谱系可落地。
- 优点：共享行为**结构性单源**，修复一次进入两版；功能清单即归属表的可执行形态，§4 归属表可与清单互相校验；产物仍为单文件，完全满足 §2.0 的顶层字面量约束（构建时把清单展开为静态字面量即可）。
- 缺点：引入构建链与「源码≠产物」的认知成本，贡献者须理解构建约定；存在「手改产物再回流」的治理风险（须以文件头构建指纹+只读约定防）；构建脚本本身成为新的单点（须纳入 WP-14 测试范围）。
- 测试成本：共享核心测一次；每版只测清单差异面 + golden 子集对比（§5 L1）。四方案中长期测试成本最低。
- 与现行流程衔接：现行「Go 为底板」的人工约定可平滑升级——Go 主版源码即共享核心的来源，smart/combo 的派生差异（58/144 行）正好是「功能清单+专属模块」的现成样本；combo 的个人逻辑可作私有构建目标，不进公开发布矩阵。

### 2.3 方案 C：单一脚本 + 运行时功能开关（档位预设）

- 形态：一份脚本（即现行 Go 主版的 36 开关体系），「轻量」实现为一个 profile 常量（如脚本头 `PROFILE='lite'`）或一份官方开关预设；§1.3 的 B/C 档实测即本方案的可达效果。
- 优点：零新增发布物、零漂移（同一份代码）、修复自动全覆盖；本项目今天就能落地；实测证明关组即连带不生成其规则集，资源轨指标真实下降（38→33 集、宿主 4→3），不是假轻量。
- 缺点：**呈现轨在 Bettbox 上打折**——GUI 开关名单取自脚本声明，单文件仍呈现 36 个开关全集，轻量用户的设置页复杂度不降（可见组数降了、设置面没降）；脚本内全量代码路径俱在，开关语义复杂度（两类缺失语义、整表替换）原样暴露给轻量用户；CVR 用户面对的是「改脚本头常量」，文档成本转嫁。
- 测试成本：单文件一份，但须按档位组合测（默认档 + lite 档至少两组 golden）。
- 与现行流程衔接：就是现行流程加一个常量，衔接成本为零；适合作为 B 落地前的阶段 1 与 B 落地后的兜底（构建链故障时可退回 C 出版）。

### 2.4 方案 D：共享数据定义 + 构建时裁剪

- 形态：数据表（serviceConfigs、baseRuleProviders、prefixRules）单源维护；构建时按版本清单裁剪数据行，并对函数做引用分析后剔除未用函数（tree-shaking 式），生成两份「无死代码」产物。
- 优点：产物最干净（轻量版不含全量函数体）；数据单源与 B 等同。
- 缺点：**构建复杂度与出错隐蔽性四方案最高**——函数级裁剪须处理动态引用（如按名拼装的服务构建路径），裁错一个仍被引用的函数即运行时报错，而该错误在 CVR 上 fail-open 静默、在 Bettbox 上是阻断型报错（WP-4 §1 失败模式 1），两种形态都难定位；本项目当前无可用 CI 兜底（WP-1 §6：现行 Test 套件跑不起来），上 D 等于把最高风险构建方式放在最弱质量基建上。
- 衔接：与 B 的差别只在裁剪粒度，B 的块级拼装已获得 D 的大部分收益（单源）而不引入引用分析风险。
- 判定：**不选**。待 WP-14 质量基建（golden+引用完整性检查）成熟后可重评估函数级裁剪，届时它只是 B 的构建脚本升级项，不是独立路线。

### 2.5 方案 E：单脚本 + 官方预设参数包

- 形态：脚本只发一份；另发两份「参数包」——Bettbox 侧为可导入的 GUI 开关表预设（外加一页说明），CVR 侧为需手改的开关清单文档。轻量/全量只是预设之别。
- 优点：发布与维护面最小；对存量用户最友好（不换脚本链接即可切档）。
- 缺点：轻量是否成立取决于用户是否正确套用预设，且 Bettbox 开关表整表存储/整表回注的语义下，预设与用户既有表的合并行为不完全可控（WP-10/WP-4 §2）；CVR 侧退化为纯文档，无强制力；呈现轨同样不降（脚本声明的开关全集不变）。
- 判定：不作为独立版本方案；作为 C 的交付包装保留——阶段 1 用「C 的 profile 常量 + E 式预设包」双通道发布，B 落地后 E 退役。

### 2.6 比较汇总与推荐

| 维度 | A 双独立脚本 | B 共享核心+清单构建 | C 单脚本+开关档 | D 数据单源+函数裁剪 | E 单脚本+预设包 |
|---|---|---|---|---|---|
| 漂移风险（R-003） | 高（人工同步） | **低（结构性单源）** | 无（单产物） | 低 | 无（单产物） |
| 呈现轨可达性 | 满（独立开关子集） | 满（清单决定声明面） | 部分（组降、开关面不降） | 满 | 弱（靠用户套用） |
| 资源轨可达性 | 满 | 满 | 满（实测证） | 满 | 同 C（取决于套用） |
| 测试成本 | 最高（×2 全量） | 最低（核心一次+差异面） | 中（多档 golden） | 高（构建本身要测） | 低 |
| 构建/治理成本 | 无构建、高同步成本 | 中（构建脚本+产物治理） | 无 | 最高 | 无 |
| 引擎形态风险 | 无 | 低（整段拼装） | 无 | **高（裁剪错误×CVR 静默）** | 无 |
| 与现行派生流程衔接 | 即现状 | 平滑升级（差异行即清单样本） | 零成本 | 需新建裁剪器 | 零成本 |

**推荐：目标形态 B，过渡形态 C+E，明确否决 A（长期）与 D（现阶段）。**

一句话理由：只有 B 同时满足「共享行为单源（解 R-003）」「产物保持单文件静态字面量（合 §2.0 引擎约束）」「归属表可执行化（清单即 §4 的机器可校验形态）」三件事，而其构建风险有 HiClash 的同谱系先例与 §5 的三级防漂移检查兜底；C/E 先行是为了让轻量定义与归属结论不必等构建链建成才生效。

分阶段路线：
- **阶段 1（零构建改造）**：按 §4 归属表在现行 Go 线落地 profile 档位常量（lite 档 = §1.4 定义），smart 线与 combo 暂不分档；同步交付 E 式预设说明。此阶段 §5 的 L0/L2 检查即可运行。
- **阶段 2（构建化）**：抽取共享核心与功能清单，构建脚本生成 lite/full 两产物（Go 线）；smart 线以「全量 + Smart 模块」并入同一构建（其 58 行 diff 是现成的模块化样本）；combo 保持私有构建目标或继续人工派生（二选一由所有者定，见 §7）。此阶段启用 §5 的 L1 golden 子集对比。

## 3. 两版必须一致的行为与允许差异的边界

### 3.1 必须一致（共享核心的定义域，差异即缺陷）

1. **输入契约**：含 proxy-providers 即抛错终止；`{...config}` 铺底透传未触及字段；external-controller/secret 明确不写（WP-1 §4）。
2. **配置哲学**：连接面字段「缺失（`=== undefined`）才补默认、已设一律尊重」；端口类故意不补（socks/redir/tproxy）的既定取舍。两版不得出现一版尊重、一版覆写的分裂——这是 WP-4 §8 人群的核心购买理由。
3. **节点标准化管线**：零宽/不可见字符剥离、toMatchableName 归一、地区/倍率识别正则、改名 + renameMap + fixDialerProxy 引用修复、未知字段展开复制保留。四项任一漂移都会造成「同订阅在两版节点池不同」的不可解释行为。
4. **DNS 安全默认全套**：fake-ip 模式与过滤合并语义、respect-rules、nameserver/default-nameserver/direct-nameserver 的分工与现行上游选择、策略子项（nameserver-policy 等）合并而非替换、DNS 引导不依赖被代理域名解析的既有安排（细节以 WP-6 结论为准，两版同步采用）。**DNS 是章程级安全面，不允许以「轻量」为名削减或改道。**
5. **规则优先级骨架**：prefixRules → STUN 段 → QUIC 段 → 服务规则 → 兜底五条（cn 直连 / geolocation-!cn 默认代理 / cn_ip / private_ip / MATCH）的相对顺序。服务规则的**集合**可随版本增减，骨架顺序不可变。
6. **开关门禁语义**：分流组/规则/规则集三处「`=== false` 才跳过」与默认关型开关「缺失=关」的两分分类，同名开关在两版的分类归属必须一致。
7. **组公共参数**：groupBaseOption 家族（健康检查目标、interval、empty-fallback 等）。注意 R-010 前提：empty-fallback 填组名在官方主线 v1.19.33 parser 报错（SRC-468），两版一致不等于两版正确；若后续按 WP-2/WP-10 结论改为节点名回填或加兼容处理，**必须两版同改、同版发布**，不得只修一版。
8. **同名开关的语义与默认值分类**：同一开关在两版含义相同；默认值允许不同（这正是分版的意义），但差异必须且只能来自 §4 归属表的显式声明（阶段 1 为 profile 表、阶段 2 为功能清单），不得在代码里散落硬编码差异。
9. **WebRTC 防护语义**：开关 1（走代理）默认开、开关 2（屏蔽 STUN）默认关、开关 2 优先于开关 1、显式 `udp:false` 保留——双开关的组合语义与优先级两版一致（失效条件文档化要求见 §4 F-34）。
10. **过滤安全默认**：过滤低/高倍率默认关、过滤非地区默认开且被过滤清单可输出自查（透明度要求，两版同）。

### 3.2 允许差异（且仅限以下范围）

- 服务组集合及其默认开/关档（以 §4 为唯一清单）；
- 随服务组增减的规则条目与规则集集合（骨架内增减，不动骨架顺序）；
- 倍率族的呈现组织（分组折叠与否）与图标子集；
- Smart 专属开关 5 个与 Smart 组型（仅 smart 线，与 lite/full 维度正交，不得用 lite 之名砍 Smart 核心参数）；
- 文件头版本标识与构建指纹（§6）；
- combo 的一切个人专属逻辑（不进公开发布矩阵，不参与双版一致性判定）。

### 3.3 灰色地带裁定原则

未列入 3.1/3.2 的行为，默认归入 3.1（必须一致）。理由：分版的合法性来自「差异被穷举声明」，未声明差异一律按漂移处理，由 §5 的 L1/L2 检查兜住。

## 5. 防漂移自动化检查设计（最小可行版）

设计约束先行：本项目当前**没有可用的 CI 测试基建**（WP-1 §6 实测：现行 Test 套件指向已归档文件、在自家仓库跑不起来；format_and_test 的触发分支与现行分支模型错位；唯一活着的是 rules-canary 依赖探活）。因此防漂移设计必须**本地可跑、零 CI 前置**，分三级随 WP-14 基建成熟逐级启用。对照范本是 HiClash（shared 单源块 + sync-shared.js 同步 + 漂移检查 + golden 30 场景哈希 + perf-guard + 真实内核运行测试，SRC-465）——其完整形态是目标，本节只取与双版一致性直接相关的最小子集；真实内核运行测试与规则内容基线归 WP-14，不在此重复索取。

### L0 共享段哈希校验（阶段 1 即可用，纯本地 Node 脚本）

- 做法：两版源码（阶段 1 为 Go 主版的 profile 双档不涉及双文件，此级先用于 Go / Go-smart / combo 三件套的既有派生关系，正是 R-003 的现行战场）中，以哨兵注释划界共享段（如 `// [SHARED:node-pipeline] ... // [/SHARED]`），脚本逐段提取并计算 sha256，两两比对，不一致即非零退出并打印段名与两版行号。
- 划界原则：段以 §3.1 的必须一致域为界（节点管线、DNS 构建、骨架规则、门禁函数）；serviceConfigs 数据表不整表划界（集合允许差异），只划其结构定义与公共字段。
- 成本：一个脚本 + 在源码加哨兵注释；发布前人工执行并把输出记入发布记录。零 CI 依赖。

### L1 双产物 golden 子集对比（阶段 2 启用，需构建产物）

- 做法：固定合成夹具（直接复用 WP-11 的夹具生成器与固定种子 20261028，保证跨次可复现）分别跑 lite/full 两产物 `main()`，对输出做**分域断言**而非整文件哈希：
  - 必须一致域逐字节（规范化 JSON 后）哈希相等：`dns`、`hosts`、兜底五条规则、节点标准化后的 `proxies`（同输入下）、连接面补默认结果；
  - 允许差异域只做集合差集断言：两版组名差集、规则集键差集必须**恰好等于** §4 归属表声明的差异集（多一项或少一项都失败）；
  - 呈现域：可见组数、规则集数对 §1.4 定额做上限断言（轻量超限即红）。
- 与 HiClash golden 的差异：其为整输出 30 场景哈希；本项目整输出含版本标识与图标子集等合法差异，整哈希必然误报，故用分域子集——这是结合本项目现实的必要裁剪，不是降标。

### L2 开关集与默认值一致性断言（阶段 1 即可用）

- 做法：用与 Bettbox `extract_options` 相同的手法（只执行顶层、提取 `ruleOptionsEnable` 与 profile 表），断言：(i) 两版（或两档）开关**键集差集**恰好等于弃用/专属声明（当前应为：lite/full 键集全等、smart 线多 5 个 Smart 键、F-29 在弃用版次后两版同步消失）；(ii) 逐键默认值差集恰好等于 §4 声明的 6+1 项；(iii) F-23 等有死开关史的开关在两档输出中均产生可观测差异（防死开关复发的最小行为断言，夹具法同 L1)。
- 价值：这一级直接把 §4 归属表变成可执行契约——归属表改一行，断言必须同步改，文档与代码从此不可能静默分家。

### 执行与门禁

- 三级检查的运行入口统一为一个本地命令（如 `node tools/check-variants.mjs`)，输出 PASS/FAIL 与差异摘要；**发布前未跑或未 PASS 不得发布**（流程门禁，人工执行、记录留痕），与 rules-canary 的依赖探活并列为发布清单两项。
- CI 化（把上述脚本挂进修正触发分支后的 workflow）是 WP-14 的工作，本节只要求脚本本身 CI 无关地可运行。

## 6. 版本标识、升级与回滚

### 6.1 标识

- 文件头三元组：`版本：x.y.z-lite` / `x.y.z-full`（现行文件头已有版本号与双地址行的既有格式，在其上加版本档后缀，不另起炉灶）；smart 线为 `x.y.z-smart`（全量档，不再叠 lite 后缀，见 §7 拍板 7）。
- 构建元数据注释（阶段 2 起）：源 commit 短哈希、构建时间、**共享段指纹**（§5 L0 的共享段哈希集短指纹）。用户报障时凭指纹即可判定其产物代次与共享段是否被改动过——这是双产物时代替代「你用的是哪一版」口头确认的最低成本手段。
- 内部断言锚点：产物内保留一行机器可读注释（如 `// variant: lite; profile-hash: <§4 声明的默认值差集哈希>`），供 L2 断言与用户自查。

### 6.2 升级

- **同档升级**（lite→lite、full→full)：走原订阅地址自动更新，版本号递增规则为工程默认（见 §7）：共享核心或任一功能行为变更升次版本，纯规则清单/注释修订升修订号。
- **跨档迁移**（lite→full 或反之）：必须更换订阅地址（两档是两个产物/两条链接），发布说明须给出迁移三步：换链接 → 打开 GUI 开关页逐项复核（Bettbox 整表回注语义下，新脚本的开关声明面与默认值以新脚本为准，旧表残留键无害但不生效）→ 按自检清单验证组数与 DNS。CVR 用户为改订阅覆写链接并复核手改项。
- **键名变更的迁移**（F-33 改名、F-29 移除若获拍板）：必须单独列入当版发布说明的「破坏性变更」节，并利用 §4 已论证的无漂移性（两者现值均与新缺失语义一致）在说明中明示「无需手动处理」。

### 6.3 回滚

- 每个发布版次以 git tag 钉住（参照 HiClash 图标以 tag 版本化的思路，脚本本身同样以 tag 提供稳定地址），订阅地址提供「当前版（分支）」与「钉版（tag）」两种形态；出问题时回滚动作 = 把订阅切回上一 tag 地址，用户侧零代码操作。
- 发布方回滚：新版发现共享核心级缺陷时，**两档同时回滚**（共享单源意味着缺陷大概率双版同源，只回一版会造成新的不一致）；功能模块级缺陷可只回对应档。
- jsDelivr 通道发布须把缓存 purge 列入发布与回滚清单两处（本项目已有 purge 实践与教训，规则集换源一事即前例）。

## 7. 待所有者拍板清单 vs 工程可默认清单

### 7.1 必须由项目所有者拍板（产品决策，不得由工程默认）

1. **F-18 Financial 轻量默认关还是开**（本文件建议关，与 WP-4 分歧 1）——本质是「轻量版为谁优化」的定位问题：新手零困惑优先，还是风控人群误走节点的尾部风险优先。
2. **F-20 AdBlock 轻量强度档与门禁**：轻量用较低强度档（广告+隐私）还是与全量同用完整版；以及「分级未落地则轻量默认关」的门禁是否接受（分歧 2）。
3. **是否增设第三档「极简」**：地板档数据已实测备查（37 组/27 集/约 640 KiB 估算），增设即多一条发布与测试线；与软路由定位（拍板 8）联动。
4. **F-33 改名是否执行**：新名 `DNS IPv6 解析` 涉及存量用户 GUI 显示与文档全量替换；本文件已论证无行为漂移，但改名本身是产品动作。
5. **F-31/32 三态合并的启动时点**：等 Bettbox GUI 非布尔承载验证（交 WP-10/WP-14）后再行，还是先在文档/CVR 侧呈现三态概念、GUI 侧维持双布尔过渡。
6. **目标形态投入**：确认走方案 B 的构建化路线（阶段 2），还是长期停留在 C 的单脚本双档——涉及是否接受「源码≠产物」的长期维护形态。
7. **smart 线是否出 lite 档**：本文件建议不出（Smart 人群本身是进阶人群，且开关面已 +5）；若所有者希望 smart 线也覆盖轻量人群，需重新评估呈现预算。
8. **轻量版是否承诺软路由/裸 Mihomo 场景**：该承诺取决于 R-010（empty-fallback 跨内核冲突）的处置优先级与产物形态（裸 mihomo 需完整 YAML 交付），属定位决策而非脚本参数问题；在拍板前，轻量版对外口径不得宣称软路由支持（与 WP-4 §4 一致）。

### 7.2 工程可默认（无需拍板，执行时按此办理，变更时记决策日志即可）

- 哨兵注释的格式与共享段划分粒度（§5 L0）；
- golden 夹具的种子、规范化 JSON 的键排序方式、哈希算法（sha256）；
- 版本号递增规则（§6.2）与 tag 命名（`v<x.y.z>`）；
- 构建脚本的目录布局、profile 表/功能清单的文件格式（以可被 L2 直接读取为准）；
- 发布记录模板与 purge 清单的具体条目；
- F-29 弃用的具体移除版次（拍板的是「弃用」本身，已由 WP-4 提出、本文件复核接受，最终确认随拍板 1–8 一并过会即可）。
