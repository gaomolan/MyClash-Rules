4. **证据驱动。** 官方文档、源码、版本发布说明、测试结果、Issue/PR、社区讨论要分开标注。社区观点不能直接作为技术事实。

8. **阶段评审。** 每个阶段结束时对照验收标准做自检。未通过时，补做工作或提交有明确理由的偏差说明，不得把未完成写成完成。
9. **不编造。** 不虚构仓库内容、用户数据、测试结果、竞品能力、项目数据、性能结论、引用或许可证状态。
10. **自主工作，不要求用户逐步批准。** 除非遇到不可逆操作、需真实凭据、必须用户提供信息或涉及外部写入操作，否则继续推进并记录假设。

## 1.2 项目状态定义

所有工作包只能使用以下状态之一：

- `NOT_STARTED`：尚未开始
- `READY`：前置条件满足，可以开始
- `IN_PROGRESS`：正在执行
- `BLOCKED`：存在阻塞，需记录阻塞原因与替代路径
- `IN_REVIEW`：执行已完成，正在验收
- `REWORK`：验收失败，需要返工
- `DONE`：符合验收标准且有证据
- `PARTIAL`：只完成部分，明确未完成范围
- `N/A`：经解释后确认不适用

不得只使用“完成百分比”代替任务状态。百分比仅可作为补充估算。

## 1.3 优先级定义

- **P0 — 决策阻断项：** 不完成就无法安全确定项目定位、重构路线或技术边界。
- **P1 — 必须完成项：** 影响方案可靠性、主要功能、安全或兼容性。
- **P2 — 重要深化项：** 能提升方案质量，但不一定阻断当前阶段决策。
- **P3 — 可选探索项：** 低概率/低影响问题、未来扩展或暂不必要的研究。

## 1.4 证据等级

每条重要结论必须标注证据等级：

- `E0 — 无证据`：个人猜测或待研究问题，不能支持结论。
- `E1 — 线索`：单一社区讨论、二手说明、未核实的经验。
- `E2 — 文档支持`：官方文档、源码注释、正式发布说明或明确的维护者说明。
- `E3 — 交叉印证`：多个独立且可信的来源一致，或源码与文档相互印证。
- `E4 — 实测验证`：可复现的实验、测试输出或直接源码运行结果。
- `E5 — 生产/跨环境验证`：在明确记录的多个真实但安全的测试环境中重复验证。当前任务不要求接触生产秘密，也不要求必须达到 E5。

对“官方支持”“默认行为”“性能更快”“能防泄漏”“兼容某客户端”等高影响主张，优先要求 E3/E4。证据不足时必须降低结论强度。

## 1.5 研究记录格式

每个研究主题使用统一结构：

1. 问题与决策关联
2. 当前假设
3. 检索范围与检索词
4. 已查来源
5. 关键事实与引用
6. 反例或矛盾证据
7. 已验证/未验证部分
8. 对本项目的影响
9. 结论与置信度
10. 建议动作
11. 需要新增的任务
12. 研究日期与研究者/Agent 角色

# 2. 项目阶段与质量门禁

项目分为 8 个阶段。后续阶段不得无条件跳过前置门禁。

| 阶段 | 名称 | 主要目的 | 通过门禁 |
|---|---|---|---|
| G0 | 项目启动 | 建立治理与研究环境 | 管理文件、范围、权限边界完整 |
| G1 | 现状基线 | 确认仓库、脚本、依赖和真实差异 | 基线可追溯、关键文件覆盖 |
| G2 | 生态与需求 | 形成竞争环境、用户需求和技术生态图 | 证据充分、竞品可比较 |
| G3 | 技术尽调 | 研究核心配置语义与高风险行为 | P0 技术问题有证据或明确阻塞 |
| G4 | 安全与许可 | 分析依赖、数据、许可证与供应链风险 | 重大法律/安全风险有处理建议 |
| G5 | 产品与架构选项 | 比较轻量/全量边界及重构路线 | 有至少 3 个可比较方案 |
| G6 | 验证策略与路线图 | 制定测试、兼容性与后续任务计划 | 任务可执行、可验收、依赖明确 |
| G7 | 独立审查与结项 | 反向验证研究质量并交付档案 | 重大缺陷清零或被明确接受 |

每个门禁必须记录：
- 计划交付物
- 实际交付物
- 验收项目
- 通过/不通过
- 未解决问题
- 对下一阶段的影响
- 评审日期

## WP-1：仓库与源码基线审计（P0）

### 目标
准确理解用户当前正在使用的代码，不基于过期记忆或 README 推断。

### 任务
- WP-1.1 确认仓库可访问性、默认分支、目标分支、当前 HEAD、最近提交和发布标签。
- WP-1.2 记录目标仓库完整文件树，识别脚本、规则、图标、文档、工作流和生成产物。
- WP-1.3 对每个脚本变体记录路径、行数、文件 hash、版本头、来源、目标客户端与内核。
- WP-1.4 读取完整 README、LICENSE、贡献指南、工作流和测试文件。
- WP-1.5 比较 `mihomoScript-custom.js`、`mihomoScriptGo.js`、Smart 变体及其他实际存在的脚本。
- WP-1.6 获取上游 `AIsouler/MyClash` 对应版本和当前版本；若无法确定对应版本，记录比较限制。
- WP-1.7 对比上游与派生代码：新增、删除、修改、配置行为变化、外部 URL 变化。
- WP-1.8 查找重复实现、分叉漂移、命名不一致、过时注释、死代码与隐式耦合。
- WP-1.9 绘制主要数据流：输入配置 → 节点过滤/标准化 → 代理组生成 → 规则集合并 → DNS/顶层配置处理 → 输出。
- WP-1.10 梳理函数调用关系、全局变量、模块边界、开关到行为的映射。
- WP-1.11 列出所有配置字段读写位置、默认值、覆盖策略和字段优先级。
- WP-1.12 建立现状功能清单，注明每项功能的代码位置、依赖、开关、风险、测试情况。
- WP-1.13 在隔离环境执行静态检查，记录工具与结果；不得修改源仓库。
- WP-1.14 识别现有测试覆盖与无法验证的行为。
- WP-1.15 输出基线审计报告与源码理解图。

### 重点审计点
- 是否对客户端已有字段采取“读取现有值、缺失才补默认”。
- `undefined`、`null`、`false`、`0`、空字符串和空数组的语义是否被正确区分。
- 配置覆写是合并、替换还是有条件写入。
- 不同脚本版本是否存在默认值不一致。
- 是否有重复或冲突的规则集键、代理组名、规则顺序。
- 是否存在节点过滤后组引用失效、空代理组、重名节点、`dialer-proxy` 断链。
- 是否对订阅节点的未知字段进行无意破坏。
- 是否存在依赖固定 CDN、特定仓库分支或单一规则源的情况。
- 是否有功能仅靠注释宣称实现但没有可验证证据。

### 交付物
`repository_inventory.csv`、`script_variant_matrix.csv`、`upstream_diff_report.md`、`current_behavior_catalog.md`、`dependency_inventory.csv`。

### 验收标准
- 所有实际存在的主要脚本变体均被纳入。
- 重要结论指向具体文件/行或 commit。
- 未访问的路径、无法取得的历史版本明确记录。
- 至少对核心处理流程与配置优先级形成可读解释。
- 不允许仅凭文件名或 README 断定功能实现正确。

## WP-2：Mihomo 官方技术规范与版本演进（P0）

### 目标
建立准确的技术事实基线，避免沿用过期参数或误解配置语义。

### 研究主题
- 官方配置文档结构与字段语义。
- Script 覆写/扩展机制及其适用边界。
- 代理节点 schema 与协议字段。
- Proxy Group 类型、参数、fallback、健康检查、lazy、tolerance、exclude-type、empty-fallback 等。
- Rules、Rule Providers、规则匹配顺序与格式。
- DNS、nameserver、fallback、nameserver-policy、direct-nameserver、fake-ip、fake-ip-filter、respect-rules 等。
- IPv6 顶层开关与 DNS IPv6 解析的区别。
- UDP 相关节点字段和网络行为。
- Sniffer 与 `skip-domain` 行为。
- TUN、路由、进程匹配、接口和平台相关配置。
- Geo 数据库、MRS、MMDB、规则格式和更新机制。
- 字段废弃、重命名、默认值变化、版本新增功能。
- 不同内核分支的配置差异。
- 官方文档与实现代码发生不一致时的判断方法。

### 执行步骤
1. 优先查官方文档、官方仓库源码、正式 Release 和迁移说明。
2. 对每个高影响字段建立“字段语义卡”：
   - 字段名、类型、默认值
   - 支持版本/首次出现版本（有证据才填）
   - 文档语义
   - 实际代码读写位置
   - 对客户端覆写的影响
   - 兼容性风险
   - 验证方法
3. 对不确定字段在隔离环境做最小化实验。
4. 比较用户目标内核版本与官方稳定版本/候选版本的差异。
5. 对文档没有明确规定的行为标为待实测，不得自行补全语义。

### 交付物
`mihomo_config_semantics.md`、字段语义表、版本差异表、官方来源登记。

### 验收标准
- 高风险配置字段均有可追溯来源。
- 官方文档、源码推断与实验结果分开标注。
- 没有来源支持的“默认值/兼容性”结论不得写成确定事实。

- 不能只挑选知名项目；需要包括直接竞品、基础设施项目和替代方案。
- 优先研究仍在维护、有明确代码或文档的项目。

- 项目定位、目标用户、支持客户端/内核。
- 配置方式、模块边界、生成逻辑。
- 规则集来源与更新方式。
- 是否有轻量/全量/模块化配置。
- 自动化测试、CI、版本发布与回滚。
- 文档、安装流程、迁移说明。
- Issues 中反复出现的问题。
- 许可证、依赖、贡献方式。
- 可借鉴之处、不可直接照搬之处。
- 证据链接与最后验证日期。

### 社区问题研究方法
- 对每个核心项目检索 README、Issues、PR、Release、Discussions。
- 以关键词覆盖 DNS、IPv6、Fake-IP、规则集更新、节点匹配、客户端兼容、性能、启动失败、规则冲突等主题。

- 记录样本范围和检索偏差，不把少量帖子当成整个用户群体的统计结论。
- 对高影响问题尽可能交叉核对源码或官方文档。

`competitor_matrix.csv`、`upstream_ecosystem_map.md`、`community_issue_evidence.csv`、`client_kernel_matrix.csv`。

### 验收标准
- 对比维度统一，能进行横向比较。
- 每个重要判断有可打开的来源。
- 清楚区分事实、社区意见与本项目的推论。

## WP-5：轻量版与全量版边界研究（P0）

### 目标
制定清晰、可维护、可测试的双版本策略，而不是简单复制两份代码。

### 至少比较以下方案

**方案 A：两份独立脚本**
- 优点、缺点、分叉风险、维护成本、测试成本。

**方案 B：共享核心 + 两份功能清单生成不同产物**
- 模块边界、构建方式、运行环境限制、生成产物与测试方式。

**方案 C：单一脚本 + 运行时功能开关**
- 用户配置难度、复杂度、运行时分支、不同客户端的配置能力。

**方案 D：共享数据定义 + 构建时裁剪**
- 规则集、策略组、图标、功能模块如何被包含或排除。

可提出其他方案，但必须与上述方案比较。

### 需要明确的产品问题
- “轻量”究竟指代码体积、代理组数量、规则集数量、内存/启动开销、外部依赖数量，还是配置复杂度？
- 哪些基础行为必须在两版一致？
- 是否共享 DNS、安全默认值、节点标准化和规则优先级？
- 高级功能怎样被显式启用？
- 如何防止两版默认值漂移？
- 如何确保修复同时进入两版？
- 是否需要单独的“极简模式”或模块化发行产物？
- 不同版本如何标识、升级、回滚和报告问题？

### 交付物
`lite_full_boundary_options.md`，包含功能归属表、方案比较表、风险和推荐理由。

### 验收标准
- 至少比较 3 种方案，推荐方案必须有明确依据。
- 明确轻量版的可测量定义。
- 定义两版共享行为和允许差异的范围。
- 给出防止版本漂移的自动化检查建议。

## WP-6：DNS 与解析链路专题（P0）

### 目标
建立对 DNS 解析、分流、Fake-IP 与规则匹配的可验证模型。

### 调研内容
- redir-host 与 fake-ip 的差异和适用边界。
- fake-ip-filter 的匹配行为与维护方式。
- `nameserver`、`fallback`、`nameserver-policy`、`default-nameserver`、`direct-nameserver` 等字段之间的职责。
- `respect-rules`、`proxy-server-nameserver` 与规则路由的相互关系。
- DNS 请求本身的路由、代理与直连行为。
- DNS 引导域名解析、规则集下载和代理节点服务器域名解析之间的依赖。
- 国内域名/国外域名分流策略与误判风险。
- DoH、DoT、普通 DNS 的安全、可用性和依赖。
- DNS 污染、劫持、缓存、冷启动和失败回退。
- IPv4/IPv6 查询结果对连接行为的影响。
- `dns-hijack` 与 TUN 的作用范围及副作用。
- 不同客户端是否会接管或覆盖 DNS 配置。

### 必须建立的模型
1. 域名查询流程图。
2. DNS 请求路由决策表。
3. 规则集下载与代理节点解析的引导依赖图。
4. 配置字段优先级与覆盖矩阵。
5. 失败场景与恢复路径表。

### 实验建议
使用虚构域名、测试 DNS 服务或可控的本地实验环境；不得使用用户真实凭据。至少设计：
- 国内/国外域名解析路径。
- 规则集 URL 不可达。
- DNS 上游不可达。
- 代理节点使用域名且 DNS 未就绪。
- 客户端 DNS 覆写与脚本 DNS 覆写冲突。
- IPv6 解析开关与顶层 IPv6 设置组合。

### 交付物
`dns_fakeip.md`、流程图、实验用例、配置风险表。

### 验收标准
- 能说明正常路径、失败路径和循环依赖。
- 所有实验标注环境和局限。
- 不将“DNS 配置启用 IPv6”与“所有 IPv6 流量被禁用”混为一谈。

## WP-7：IPv6、UDP、WebRTC/STUN、QUIC 专题（P0）

### 目标
明确不同开关的真实控制范围、潜在副作用与测试方法。

### 研究内容
- 顶层 IPv6 设置与 DNS IPv6 解析的差异。
- 代理节点 `udp` 字段的默认行为与显式 `udp:false` 的保留原则。
- UDP 流量是否经过代理、由谁决定、如何验证。
- WebRTC 的 ICE、STUN、TURN 及不同传输方式。
- 常见 STUN/TURN 端口规则的覆盖范围与漏网可能。
- 屏蔽 STUN 是否会破坏语音、视频、游戏或会议应用。
- 代理 UDP 的兼容性与不同节点协议的限制。
- QUIC（尤其 UDP 443）拦截对 HTTP/3、视频、浏览器和应用的影响。
- 私有地址、内网服务与 STUN 端口规则之间的例外处理。
- 双开关组合的行为定义与优先级。
- “走代理”“阻断”“直连”“不处理”之间的语义边界。

### 必须交付
- 开关行为真值表。
- 规则顺序与命中解释。
- 功能覆盖边界说明。
- 客户端/内核/协议的验证矩阵。
- 误伤场景与回退方法。

### 最低测试组合
对 WebRTC 代理开关与 STUN 屏蔽开关进行全组合测试；另行覆盖 IPv6 开关、节点 UDP 显式值和缺省值、QUIC 规则开关的交互。每种组合都记录预期配置、实际配置、验证方式和结果。

### 验收标准
- 不宣称常见端口拦截可以阻断全部 STUN/TURN。
- 不宣称将 `udp:true` 写入节点就能保证所有 WebRTC 流量经代理。
- 明确脚本能够控制的范围与客户端/操作系统无法由脚本保证的范围。

## WP-11：性能、资源与冷启动研究（P2）

### 目标

## WP-12：安全、隐私与供应链审查（P0）

### 目标

- 外部 JS、规则集、Geo 数据、图标、CDN 和远程脚本依赖。
- URL 是否固定到 tag/commit，还是使用可变分支。

### 威胁建模

- 远程依赖被篡改。
- 规则集源失效或返回错误数据。
- 客户端字段被意外覆盖。
- DNS/路由规则导致流量走错出口。
- 真实订阅/节点凭据被写入公开报告。
- 上游更新引入回归。

### 验收标准

- 风险等级有定义，不能只写“高/中/低”而无依据。
- 不将“使用 HTTPS”视为完整的供应链安全方案。

## WP-14：自动化测试与质量工程设计（P0）

### 目标
为未来重构建立可执行的质量体系，防止功能改动导致隐性回归。

### 测试层次
1. 静态检查：语法、格式、重复键、未使用代码、危险模式。
2. 单元测试：节点名称匹配、倍率识别、配置字段合并、规则生成等纯逻辑。
3. 属性测试：输入配置不应被意外破坏、输出引用应保持一致等不变量。
4. 快照/黄金文件测试：固定输入生成配置与预期输出对比。
5. Schema/配置校验：使用适当版本的 Mihomo 校验输出；若工具不能完整校验 Script 输出，要明确限制。
6. 集成测试：模拟输入配置与脚本处理链路。
7. 兼容性测试：客户端/内核版本矩阵。
8. 回归测试：每次变更前后对比。
9. 外部依赖测试：URL 不可达、超时、错误格式、空数据、CDN 缓存。
10. 故障注入：DNS 失败、规则集失败、空节点、无匹配地区、无效默认组。
11. 性能基准：节点规模与规则规模变化。
12. 安全测试：敏感信息扫描、远程依赖清点、输出脱敏。

### 必测不变量
- 不应无故丢失原始代理节点的未知字段。
- 明确的用户值不应被脚本默认值覆盖，除非功能规格明确要求覆盖。
- 不应生成指向不存在代理组的规则。
- 不应生成重复的策略组名称或规则集键。
- 过滤后不得留下无法解释的空组。
- 节点重命名后，引用关系应保持有效或被安全移除。
- `udp:false` 等显式用户配置应按规格保留。
- 功能关闭时，不应残留与该功能绑定的规则、组或 Provider。
- 轻量版与全量版共享的核心行为应通过相同测试。
- 生成失败应有明确错误，而非静默输出看似有效的错误配置。

### 交付物
`test_strategy.md`、`test_case_catalog.csv`、测试夹具、质量门禁方案。

### 验收标准
- 每个 P0 风险至少映射一个测试用例或明确的外部验证任务。
- 每项核心功能有正向、负向和边界测试。
- 说明哪些测试可在 CI 自动执行、哪些需要手工或真实客户端。
- 不得把“有测试计划”表述成“测试已通过”。

## WP-15：架构方案与重构路线比较（P0）

### 目标
基于证据选路线，而不是预先认定从零重构最优。

### 至少比较四条路线

**路线 A：渐进重构现有派生脚本**
- 逐步清理重复、拆分逻辑、补测试、统一默认值。

**路线 B：保留现有行为规格，重写共享核心**
- 先锁定输入输出行为，再重写核心处理逻辑。

**路线 C：从零设计模块化生成器**
- 明确数据定义、功能模块、构建过程与发行产物。

**路线 D：围绕上游维护薄层补丁**
- 尽量减少复制代码，依靠上游，维护独立补丁和特定功能。

可以提出额外路线，但不能省略以上比较。

### 统一评估维度
- 现有功能保留能力。
- 技术风险。
- 迁移成本。
- 测试难度。
- 兼容性维护成本。
- 上游同步成本。
- 版本分叉风险。
- 可扩展性。
- 可读性与新贡献者理解成本。
- 依赖与发布复杂度。
- 轻量/全量双版本支持。
- 回滚能力。
- 对用户现有配置的破坏风险。

### 决策方式
- 给出权重和评分理由。
- 不要用伪精确分数掩盖证据不足。
- 做敏感性分析：调整关键权重后推荐方案是否改变。
- 明确不可妥协约束。
- 对推荐路线列出前置条件、反对意见、失败风险和回滚策略。

### 交付物
`architecture_options.md`、ADR（Architecture Decision Record）草案、推荐路线及反证。

### 验收标准
- 至少四条路线完整比较。
- 推荐理由可追溯到现状基线和风险研究。
- 明确说明为什么不选其他路线。
- 结论不是仅依据“代码更干净”或“从零更自由”。

- 证据不足处已降级表述或标为待验证。
- 报告与任务台账、风险登记册、决策日志一致。
- 明确列出项目不能回答的问题及原因。

# 5. 风险登记册与阻塞管理

## 5.1 风险登记册字段

```csv
risk_id,title,category,description,likelihood,impact,risk_score,priority,trigger,mitigation,contingency,owner,related_tasks,evidence,status,last_reviewed
```

风险类别至少包含：
- 技术语义误判
- 客户端兼容性
- 内核版本差异
- DNS/路由安全
- 外部依赖失效
- 许可证/版权
- 上游变更
- 自动化测试不足
- 双版本漂移
- 文档与代码不一致
- 研究范围膨胀
- 环境或权限阻塞
- 证据来源不可靠

## 5.2 风险评估

使用 1–5 级可能性和影响；风险分数可用 `可能性 × 影响` 辅助排序，但不能替代文字判断。

- 1–4：低
- 5–9：中
- 10–15：高
- 16–25：严重

严重风险必须有缓解方案、应急方案和负责人角色。无法消除的风险应记录为接受、转移或待决，不可从清单中删除以美化结果。

## 5.3 阻塞项处理

每个阻塞项必须写：
- 阻塞内容
- 对哪些任务/门禁造成影响
- 已尝试的解决办法
- 替代来源或替代实验
- 是否必须用户介入
- 继续执行的安全边界
- 最终状态

如果上游仓库、官方文档或客户端版本无法访问，继续研究其他部分，并把受影响的结论降级；不得因一个阻塞而停掉所有可独立推进的任务。

# 6. 证据收集与引用协议

## 6.1 来源优先级

1. 官方配置文档、官方仓库源码、官方 Release/迁移说明。
2. 维护者直接说明、官方 Issue/PR。
3. 竞品源码、测试与文档。
4. 有明确复现步骤的社区问题。
5. 技术文章、博客和经验分享。
6. 搜索摘要、转述、无出处观点。

较低等级来源可帮助发现问题，但关键技术结论要尽量回到源码、正式文档或可复现实验。

## 6.2 来源登记字段

```csv
source_id,title,source_type,url,repository,branch_or_version,commit_or_release,published_at,accessed_at,author_or_owner,claim_supported,evidence_level,quote_or_excerpt,limitations,related_tasks,local_snapshot_path
```

## 6.3 引用要求
- 每个关键结论都附来源 ID 或具体文件/行。
- 对 GitHub 文件优先固定到 commit 或 tag；若只能使用可变分支，明确记录。
- 记录资料发布日期与访问日期。
- 不大段复制第三方文本；以摘要和短摘录为主。
- 同一来源不应被反复引用来伪装成多源交叉印证。
- 发生冲突时保留双方证据并解释判断理由。
- 对已失效链接记录失效状态，不自行推测其内容。
- 对无法访问的页面不能引用搜索摘要作为已读全文的证据。

# 7. 实验与代码执行规范

## 7.1 实验必须具备的记录
- 实验 ID
- 研究问题
- 假设
- 环境/OS/运行时/工具版本
- 输入夹具及其 hash
- 命令或操作步骤
- 预期结果
- 实际结果
- 日志/输出位置
- 结论
- 限制与下一步

## 7.2 隔离要求
- 只在独立目录或临时分支/副本执行。
- 原仓库保持只读。
- 不将用户订阅、服务器地址、UUID、Token、密码、Cookie 或其他凭据用于公开测试。
- 测试数据优先采用合成代理节点和虚构域名。
- 所有日志在写入研究档案前做敏感信息检查。
- 不执行来源不明的脚本或二进制作为测试工具。
- 若必须下载工具，记录来源、版本、校验信息和执行理由。

## 7.3 失败结果也要保存
测试失败不等于任务失败。失败本身可能揭示风险，但必须区分：
- 被测代码缺陷
- 测试环境缺陷
- 工具版本不匹配
- 外部依赖不可达
- 预期行为定义错误
- 结果无法判定

不得把“命令执行成功”直接当作“功能验证通过”。
