> 状态：**设计定稿（本阶段交付）**，2026-10-28。配套交付：`test_case_catalog.csv`（85 条用例）、`compatibility_test_matrix.csv`（18 行）、`validation_gaps.md`、`prototypes/`（3 个已实跑原型，EXP-WP14-01/02/03）。

## 1. 目标与分层证据观

本策略要解决的根本问题（WP-1 §6 结论）：目标仓当前**没有任何可用的自动化测试**覆盖任何在用脚本——现行 Test 套件在自家仓库启动即崩溃，唯一活着的自动检查 rules-canary 只探活远程依赖、不测脚本逻辑。三件套至今靠人工实测与巡检兜底。本策略按章程 12 层重建体系，并坚持两级证据观：

- **生成级**：在 JS 沙箱中运行 `main()`，断言生成物的结构与内容。本项目迄今全部 E4 证据（WP-6/7/8/9/11 与本 WP 原型）都在这一级。它证明「脚本生成什么」，**不证明内核如何执行、客户端如何接管**。
- **运行时级**：真实 mihomo 内核/真实客户端加载并运行配置，观察解析、路由、DNS、故障降级。本项目运行时级证据目前为**零**，这是 `validation_gaps.md` 的 GAP-01，也是本策略 L5/L10 的主要建设方向。

两级不可互相替代：生成级全绿不能推出运行时可用（R-010 的 empty-fallback 语义冲突即为生成级无感、内核级致命的实例）。

## 2. 现行 Test 体系失效分析与 format_and_test 处置（R-001）

### 2.1 失效三因（WP-1 §6 实证，E4）

1. **被测对象被归档**：`Test/lib/scripts.js` 仍指向 `Script/Script.js` 与 `Script/mihomoScript.js`，两文件已于 2026-10-27 移入 `archive/`，套件在目标仓克隆内启动即 `ENOENT` 崩溃（上游克隆同套件 188 项全过，证明套件本体完好、是仓内路径漂移）。
2. **触发分支错位**：`format_and_test.yaml` 的 push 触发分支为 `['main']`，目标仓工作分支为 `myclash-rules`，push 永不触发（仅 workflow_dispatch/PR 可达）。
3. **覆盖对象错位**：即便修好路径，被测的仍是已归档的上游两脚本；在用的三件套与 custom 线从不在其范围内。另注意：上游 Test 含 ES2020/QuickJS 兼容检查（es2020-check/quickjs-check）——这类检查恰是 R-012 需要的形态，但目标仓从未运行过它。

### 2.2 处置方案（设计，属下一阶段仓库改造，本阶段不执行）

| 项 | 现行 | 处置 |
|---|---|---|
| 触发 | push→main（永不触发） | 改为工作分支（现 `myclash-rules`；新公开仓则为其默认分支）+ PR + workflow_dispatch |
| format job | prettier `--write` 后自动提交回推 | 改为 `--check` 只验不写；另设手动 `format-fix` workflow 供维护者显式触发。理由：自动回推与 sync workflow 的 rebase 推送、人工小步推送三方竞态，且「CI 改了我的代码」不可审计 |
| 被测对象 | archive 两脚本 | `Test/lib/scripts.js` 清单切换为三件套（+custom 线拼接产物冒烟，TC-I-04）；旧两脚本条目删除 |
| 测试入口 | run-tests.js（针对旧脚本的断言） | 保留 harness 骨架（loader/harness 可复用），断言集换为本目录 L1–L4/L6 用例的产品化实现 |
| 新增 job | 无 | `kernel-check` job（L5，见 §3.5）、`canary-content` job（L9 指纹，见 §3.9）、`engine-matrix` job（L7 的 qjs 格，见 §3.7） |
| 与 rules-canary 的关系 | 各自独立 | 探活保留在 canary；内容指纹（TC-X-02）并入 canary 扩展或新 job，二选一由 WP-16 排期时定，本策略不预设 |

### 3.1 L1 静态检查
在断言运行之前先拦结构性问题：语法（TC-S-01）、provider 键唯一性（TC-S-03，针对 `{...base}`+`Object.assign` 静默覆盖的代码气味）、重复键（TC-S-04，现行 `cn` 双定义以豁免清单起步）、开关一致性（TC-S-05，原型2 已验证）、死开关（TC-S-06，2026-10-20 事故的常设防线；实现注记：读取点统计须排除定义处与注释，建议以 AST 或「键名在定义块外出现次数 ≥1」的近似规则起步并登记近似性）、危险模式（TC-S-07）。工具选型说明：不引入 ESLint 全家桶——脚本为单文件无模块体系，`node --check`/`vm.Script` + 定向扫描已覆盖本层目标；prettier 只做格式门禁（TC-S-02）。

### 3.2 L2 单元测试
运行器选 `node:test`（Node 24 内置，零依赖）+ 既有 vm harness 模式（WP-1 run_variants.js / WP-9 wp9_run.js 同型）。被测函数的取得方式：脚本为单文件顶层函数声明，harness 以源码尾部追加导出钩子取出内部函数（WP-9 EXP-902 已用此法导出正则本体），或整脚本运行后做输出级断言——前者定位精确、后者不侵入，两者并用并在用例中注明。正则类单元（TC-U-01/02/03）的断言口径是**基线锁定**：断言当前行为（含 F 系列已登记的误判/漏识别），不把研究者的「设计意图」写成断言——意图分歧条目挂缺陷引用，修复正则时同步翻转基线（流程见 §5）。

### 3.3 L3 属性测试
章程 10 条不变量中 8 条落在本层（另两条：共享行为同测→TC-DV-01；生成失败显式化→TC-P-10 与 L10 生成级部分）。核心资产是**引用完整性校验器**：WP-8 一次性脚本（EXP-WP8-01）与 WP-6 校验器（EXP-INT-01）已在本 WP 合并产品化为 `prototypes/check_references.js` 并实跑（EXP-WP14-01：15 次运行、H 类硬断言 0 失败；新增 H8 校验 DNS 服务器 `#组名` 后缀）。警告项实行**基线管理**：W1（default-selected 降级，现行基线=每变体 S2 场景 4 条）等已知警告登记在册，新增警告与硬失败同级拦截——防止警告面无声扩大。开关 fuzz（TC-P-09）是本层对现状的最大补强：三联动此前只测过单点关组，36 开关的组合空间以固定种子集+增量随机种子覆盖。

### 3.4 L4 快照/黄金文件
借鉴 HiClash 的 golden 实践（30 场景输出哈希，WP-3 竞品证据）：对场景集的生成输出做**规范化 JSON**（键序固定、剔除时间戳类字段——本项目生成物本无时间字段，规范化主要处理对象键序）后取 sha256 锁定（TC-G-02）。WP-9 的 135 例夹具（TC-G-01）与 WP-6/7 的场景矩阵（TC-DNS-01/02/06、TC-W7-01/02/04、TC-DNS-04）以逐字段快照形态固化，其中 EXP 已实证者标「已有实证待固化」——固化动作是把 EXP 的运行方式转为断言式 runner 并把基线文件入仓，不是重跑一遍了事。黄金基线的更新必须走 TC-R-01（变更前后 diff 人工签核），禁止 CI 自动更新基线。

### 3.5 L5 Schema/配置校验（内核接入方式与限制）
接入方式：CI 的 kernel-check job 下载 **MetaCubeX/mihomo 官方 Release 二进制**，版本钉死（如 v1.19.33），以官方发布的 checksums 校验 sha256 后执行 `mihomo -t -d <tmpdir> -f <生成配置.yaml>`；生成配置由 L6 harness 导出 YAML（需新增一个 JSON→YAML 序列化步骤，选 `yaml` npm 包或 python PyYAML，钉死版本）。内核版本升级走 TC-K-05 事件流程（人工触发、结论登记），不自动跟随最新版——与项目「精选集成」政策一致。
**限制（必须明示）**：① `-t` 只做配置解析级校验，不执行规则匹配、不验证 DNS 运行时行为；② `-t` 期间 rule-providers 的远程内容不被完整拉取校验（provider 内容正确性归 L9 与 L10）；③ smart 内核（lux5am fork）为 Prerelease-Alpha，其二进制引入须单独记录来源与校验和（TC-K-04），且结论只对该 fork 版本负责；④ 生成级 harness 用 `Object.assign` 模拟 Bettbox 开关回注（TC-I-05）不等于客户端真实合并路径，内核校验的对象始终是「脚本在默认/指定开关下生成的配置」。
本层的头号用例是 TC-K-02（empty-fallback 探针）：现行五脚本的 empty-fallback 均为 `REJECT`（内置 proxy 名，合规），探针以最小配置分别验证「填组名→官方内核解析报错（记录原文）」与「填 REJECT→通过」，把 R-010 从源码推断（E3）升级为内核实证（E4），并锁死未来任何把 empty-fallback 改成组名的编辑。

### 3.6 L6 集成测试
沿用 vm harness 的整管线运行：结构基线（TC-I-01）、三联动（TC-I-02）、combo 隔离（TC-I-03）、入口拒绝（TC-I-06）均已实证并固化为断言；新增两件：custom 线拼接冒烟（TC-I-04，把 WP-12 给 sync 的断言集——customPatch 耦合的 4 个上游内部标识符存在性 + 生成后 `node --check` + 合成冒烟——落为 CI 用例，使上游漂移在 sync 推送前被拦）与 Bettbox 合并路径等价集成（TC-I-05，把 WP-10 的两段式模型变成生成级可测形态）。

### 3.7 L7 兼容性测试
矩阵全文见 `compatibility_test_matrix.csv`。方法分工：**引擎格**可在 CI/沙箱推进——lookbehind 探针（`prototypes/lookbehind_probe.js`，引擎无关写法）已在 V8 与现代 JSC 实跑 6/6（EXP-WP14-03），QuickJS 格以 quickjs-ng 官方 `qjs` 二进制（校验和钉死）进 CI 补齐；BoA 无独立二进制，Boa 格只能经 CVR 实机探针补（TC-C-04 附带）。**客户端格**全部需要真机/真客户端（TC-C-03/04/05），本阶段只给冒烟清单与生效性探针设计——特别地，CVR 冒烟必须包含「覆写确实生效」的探针（changed_keys 核对 + 生成标记字段），因为 CVR 失败时静默跳过（fail-open），只看启动成功会把未覆写状态误报为通过。

### 3.8 L8 回归测试
流程层：TC-R-01（diff 签核）是黄金基线的人工闸门；TC-R-02 把上游精选集成固化为「全量 L1–L4 + 差异逐条处置」清单；TC-R-03 要求 canary 报警必须先转为复现记录才关单，防止报警只看不用。

### 3.9 L9 外部依赖测试
现行 canary 只回答「URL 活着吗」，WP-3 的生态证据（meta-rules-dat 曾发布 10 个 0 字节 .mrs 静默失效）与 WP-12 的增补要求回答「内容对吗」：TC-X-02 为 38 个 provider 建内容指纹基线（sha256+字节数）。**基线管理注记**：规则集上游多为每日发布，内容变化是常态——指纹基线不能逐字锁定，须以「变化被记录+异常模式报警（0 字节、体积突变 >50%、格式头校验失败）」为准，正常日更只留痕不报警。此点与探活的「失败才报警」不同，设计时已区分。TC-X-03 把 EXP-WP8-02 的 bundle 覆盖率审计（33/38）滚动化；TC-X-04 覆盖自有图标（与 R-004 资产迁移配套）。

### 3.10 L10 故障注入
分两半：**生成级**（TC-F-01/02/03，CI 可跑）已部分实证——fail-fast 形态（TC-F-01）与畸形 name 崩溃形态（TC-F-02，EXP-905）均已锁定；TC-F-02 的断言口径是「缺陷形态登记」：当前断言的是崩溃形态与登记一致，修复落地后翻转为「跳过坏条目」断言，在此之前它是一条**常亮的已知缺陷哨兵**，不是绿色装饰。**运行时级**（TC-WP8-01~06、TC-DNS-08、TC-W7-05/06）全部依赖 GAP-01 的内核实验台：本地 HTTP 桩（node 单文件即可）+ 官方内核 + 替身上游（CoreDNS/dnsmasq）+ 替身 STUN，环境规格已在各用例与 WP-6 §8 中给出，本阶段未搭建。

### 3.11 L11 性能基准
方法与基线直接继承 WP-11（EXP-906/907/903）：固定种子合成夹具、四档规模、中位数+极差、生成级口径。门禁采「趋势报警+硬线后置」：共享 CI runner 的噪声（EXP-906 极差曾达 232ms）使硬阈值在共享环境下必然误报，故 TC-B-01 只报警；TC-B-02（借鉴 HiClash perf-guard 的 500 节点硬线）须在独占/自托管 runner 标定后才启用。内存峰值（TC-B-03）补 WP-9/WP-11 共同缺口，首次只登记不设限。

### 3.12 L12 安全测试
以「清点对账」为骨架：TC-SEC-02 把脚本内全部远程 URL 提取后与 `dependency_inventory.csv` 逐一对账，未登记的新 URL 即红——这是把供应链纪律变成机器门禁的落点；TC-SEC-03 是 R-004 的发布闸（公开候选包内组合脚本/`[Spark]` 等个人标记零命中）；TC-SEC-04 是 R-011 的发布闸（许可声明与 LIC 待确认项状态）；TC-SEC-01/05 为敏感信息与脱敏扫描（本项目夹具全合成，此二条是为发布后设的防线）。

## 4. WP-9 夹具复用方案（135 例 + 66 单元）

资产现状：`07-validation/test_fixtures/wp9-node-fixtures.json`（15 套件、135 个节点级用例，含逐例 expect）、`wp9-regex-units.json`（66 条）、`wp9_run.js`/`wp9_regex_units.js`（WP-9 运行器）、`wp9-results.json`（基线结果）。
复用方式：
1. **夹具本体零改动迁入**新套件（sha256 已登记：`1b2667fc…b65279`），作为 TC-G-01/TC-U-01/02/03/04/06 与 TC-P-01/06/07 的共同输入源；任何新增用例以新套件文件追加，不改旧夹具（保 EXP-901 可复现）。
2. **运行器产品化**：wp9_run.js 的「预测比对」逻辑改为断言式 runner（node:test 外壳），输出结构化失败清单（套件/用例/期望/实际），且把「缺陷行为按缺陷预期计通过」的口径显式编码为每例的 `expect.basis` 字段（行为基线 vs 设计意图），杜绝后人把 135/135 误读为「脚本无缺陷」——135 例中包含 F-01~F-21 的缺陷复现例。
3. **与 F 系列的联动**：F 系列每条发现至少被一个用例锁定（映射见目录 notes）；修复任一 F 项时，对应用例的基线翻转必须在同一提交中完成并在 TC-R-01 diff 中可审。
4. **变体覆盖注记**：夹具的变体对照套件（S10a/b/c）覆盖旧 smart 与 custom 线；go-smart 以「定义与 Go 逐字一致」（WP-9 E2）为由由 Go 代表，此代表性假设本身登记为 GAP-08 的一部分，待 go-smart 独立套件补齐后关闭。

## 5. CI 落点与执行频率汇总

- **每 push/PR**：L1、L2、L3、L4、L6、L12（仓库面）、L7 的 CI 格（qjs 探针）——目标总时长 < 5 分钟（生成级套件实测为秒级，主要成本在内核 job 之外）。
- **配置产物变化时**：L5 kernel-check job（内核二进制按版本缓存于 CI cache，校验和每次核对）。
- **每日**：L9（canary 探活既有 + 指纹扩展）。
- **每周**：L11 趋势基准。

## 6. 门禁规则（什么失败拦发布）

**硬拦（任一失败不得发布）**：
- L1/L2/L3/L6 任一红；L4 哈希变化未经 TC-R-01 签核；
- L3 出现警告基线外的新增警告；
- L5：TC-K-01 在目标内核版本未通过，或 TC-K-02 结论与登记不符；
- L7 CI 格（引擎探针）红；发布目标含 Bettbox 时 TC-C-03 未签核；
- L12：TC-SEC-02 对账不等、TC-SEC-03 命中、TC-SEC-04 未清零；
- L9：TC-X-02 出现 0 字节/整源失效级报警未处置。

**告警（可发布但须登记）**：TC-B-01 趋势超带、TC-X-01 单点探活抖动（复检通过）、TC-X-05 异常、TC-K-05 发现新版内核（待评估）。
**豁免流程**：硬拦项豁免须在发布记录中写明理由、影响面与补做期限，由项目所有者批准；豁免不修改基线本身（与 TC-S-04 的豁免清单同理）。
