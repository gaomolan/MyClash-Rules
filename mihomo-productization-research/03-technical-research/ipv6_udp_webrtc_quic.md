## 1. IPv6：两个开关的控制范围与我方实际实现

### 1.1 官方语义（E3，引 WP-2 语义卡 B1/A6 与底稿 §1）

| 开关 | 默认 | 控制面 | 语义 |
|---|---|---|---|
| 顶层 `ipv6` | `true` | 流量面 | 是否允许内核接受 IPv6 流量 |
| `dns.ipv6` | `false` | 解析面 | 是否解析 IPv6；false 时 AAAA 查询回应空解析 |

两者独立：顶层关不改变 DNS 应答内容；解析关不直接拦截 IPv6 字面地址连接。TUN `inet6-address` 生效需顶层 ipv6=true（E2）。

### 1.2 我方脚本的实际写入位置（源码直读 E2 + 生成级实测 E4）

脚本对 IPv6 只有两个写入点，没有第三处：

1. **`dns.ipv6`**（`buildDnsAndHostsConfig`，L1765）：`ruleOptionsEnable.IPv6总开关 === true && ruleOptionsEnable.WebRTC走代理 !== true`。即「IPv6 总开关」单独并不能打开 DNS IPv6——开关1（WebRTC走代理，默认开）在场时恒为 false。这是刻意的与逻辑（代码注释：防 STUN 经 IPv6 直连泄露），但对外呈现为一个反直觉事实：**用户打开「IPv6总开关」后，只要没关「WebRTC走代理」，DNS IPv6 依然是关的**。
2. **顶层 `ipv6`**（`main`，L1863–1865）：仅当输入未设置（`=== undefined`）**且**开关1 开启时写 `false`；输入已设（含 true）时脚本不动。「IPv6总开关」对顶层**没有任何写入路径**——开关名与实际控制面（仅 dns.ipv6）的落差由代码注释自认（「已知缺口」），且 EXP-DNS-07C 生成级实测确认：输入 ipv6=true + 开关1 开 → 输出顶层仍为 true，开关1 的防泄露意图在此组合下不成立，最终只能靠 Bettbox App 层设置兜底。

EXP-DNS-07C 全矩阵（12 组合，E4；输入=订阅/App 传入脚本前的值）：

| 输入顶层 ipv6 | IPv6总开关 | 开关1 | 输出顶层 ipv6 | 输出 dns.ipv6 |
|---|---|---|---|---|
| 未设 | 关 | 开 | **false**（脚本写） | false |
| 未设 | 关 | 关 | 未设（→客户端/内核默认 true） | false |
| 未设 | 开 | 开 | **false**（脚本写） | false |
| 未设 | 开 | 关 | 未设 | **true** |
| true | 关 | 开 | true（脚本不动） | false |
| true | 关 | 关 | true | false |
| true | 开 | 开 | true | false |
| true | 开 | 关 | true | **true** |
| false | 关 | 开 | false | false |
| false | 关 | 关 | false | false |
| false | 开 | 开 | false | false |
| false | 开 | 关 | false | **true** |

两点读解：
- 顶层输出只由「输入值 + 开关1」决定，与 IPv6总开关无关；dns.ipv6 只由两开关与逻辑决定，与输入顶层值无关。两个开关在两个层面上**互不感知**。
- 最后一行组合（输入 false + 总开关开 + 开关1 关）由脚本自身产出「解析开、流量关」状态：AAAA 有应答但流量面拒绝——正是底稿真值表草案中标为易误解的一格，现确认脚本可达此状态（生成级）。其运行时表现（应用拿到 AAAA 却连不通的回退行为）待实测（EXP-DNS-07 运行时部分）。

### 1.3 与 Bettbox 的叠加（引 WP-10，SRC-903）

Bettbox 的 App patch 在脚本之后执行，general 段（含顶层 ipv6）App 已设值时整段覆盖脚本输出。故 §1.2 矩阵在 Bettbox 场景的最终形态是：**顶层 ipv6 = App 设置（若设）＞ §1.2 输出**；dns.ipv6 不在该覆盖路径内（override-dns 默认关），**恒为脚本输出**。结论：Bettbox 用户的「IPv6 是否全关」取决于 App 设置与两开关的**三方组合**，任何单文档说明都会误导——列 WP-15 决策输入（是否在脚本注释/用户文档中固化该三方表）。

## 2. 节点 `udp` 字段：语义与实测保留矩阵

官方语义（E3，底稿 §2.1）：节点级 `udp` 默认 false（TUIC 等 UDP 原生协议与 direct/dns 类型除外）；组级 `disable-udp` 可整体禁用。UDP 是否经代理的决策链自上而下为：入站捕获（客户端/系统，脚本不可见）→ 规则匹配 → 组 disable-udp → 节点 udp 支持 → 协议实现。脚本只能影响中间三层的配置生成部分。

我方实现（`main` L1963 起，开关1 第三件套）：开关1 开启时，对 `udp === undefined` 的普通节点以展开复制补 `udp: true`；显式值（true/false）原样保留；`direct`/`reject`/`rematch` 类型跳过。EXP-WRTC-02 实测（E4）：

| 节点样本 | udp 输入 | 开关1 开 → 输出 | 开关1 关 → 输出 |
|---|---|---|---|
| 香港 ss（域名 server） | 未声明 | **true**（补写） | 未声明（不变） |
| 新加坡 trojan | 未声明 | **true**（补写） | 未声明 |
| 美国 ss | 显式 false | **false**（保留） | false |
| 日本 vless | 显式 true | true | true |
| 内置直连变体 ×5（type=direct） | 未声明 | 未声明（类型守卫生效） | 未声明 |

两点边界：
- 显式 `udp:false` 的节点在开关1 开启时**依然不承载 UDP**——这类节点的存在使「STUN 必走代理」在原理上不可由脚本保证（代码注释亦自认）。STUN 流量若被规则送往只含此类节点的组，运行时结果（失败/回退/直连）待实测，且该行为不由脚本决定。
- 直连变体不写 udp 是有意依赖内核对 direct 类型的默认 UDP 行为（语义卡注记 direct 默认开启，E2）；脚本层无显式声明，属隐性依赖，列未验证项 U-W7-4（目标内核版本上复核）。

## 3. WebRTC / STUN / TURN 协议事实与端口覆盖边界（底稿 §3 复核保留，E2）

- ICE 先经 STUN 了解公网映射（Binding），不通时经 TURN 中继；STUN/TURN 默认端口 3478（UDP/TCP）、5349（TLS/DTLS）；TURN 媒体中继端口与 ICE 媒体面（SRTP/DTLS）端口为动态协商，无固定值；TURN 可承载于 TCP/TLS（含 443 部署）。
- 因此**任何端口清单方案只能覆盖「以常见端口联系已知 STUN/TURN 服务器」一段**，覆盖不了媒体面动态 UDP、非标端口、TCP/TLS 承载的 TURN 与应用自带中继。此判定为本专题的覆盖边界结论，后续文档不得放大引用。
- 反向误伤面：语音/视频通话、会议、游戏语音、远程桌面同样使用 ICE/STUN/TURN；屏蔽后应用可能回退 TCP 中继（体验降级）或直接失败，**因应用而异，未逐个验证**。
- 浏览器自身的 WebRTC 策略（mDNS 候选、IP 处理模式）由浏览器/系统决定，脚本与内核均不可控；脚本最多决定「被捕获的流量如何路由」。

## 4. 双开关的实际实现逐条对照

### 4.1 开关1「WebRTC走代理」（默认开）——三件套，无一为路由规则

| # | 实现 | 代码位置 | 生成级实测 |
|---|---|---|---|
| ① | 顶层 ipv6 未设置时写 false | main L1863 | EXP-DNS-07C：仅「未设+开」一格写出 false；输入已设 true 时不动（缺口，§1.2） |
| ② | dns.ipv6 与逻辑（压制 IPv6 解析） | L1765 | 同上矩阵：开关1 在场时 dns.ipv6 恒 false |
| ③ | 缺省 udp 节点补 udp:true | main L1963 段 | EXP-WRTC-02：见 §2 表 |

**关键纠正（对底稿 §5 草案的修正）**：开关1 **不生成任何把 WebRTC/STUN 流量指向代理组的规则**。被捕获的 STUN 流量走的是普通规则链：prefixRules（域名集，对 IP 字面目标多不命中）→ 功能规则（各服务 IP 集，如 google_ip 等，视目标而定）→ 兜底五条（cn_ip 直连 / private_ip 直连均不命中公网 STUN 地址时 → `MATCH,漏网之鱼`）。「漏网之鱼」组成员为 `[默认代理, 直连, …地区组]`，**其实际落点是用户在客户端里的选择**（默认首选为默认代理）。因此「走代理」的准确表述是：*脚本通过补全节点 UDP 能力与关闭 IPv6 泄露面，使普通规则链有条件把 STUN 承载到代理节点上；但出口组不由脚本锁定，用户把漏网之鱼切到直连时 STUN 即直连*。开关名与机制之间的这段落差是本专题最重要的命名风险（WP-15 输入）。

### 4.2 开关2「屏蔽STUN端口」（默认关）——10 条规则，位置与原文（E4 实测）

开启时在 `rules` 数组中插入恰好 10 条（EXP-WRTC-01：默认全开配置下位于索引 11–20，即 prefixRules 11 条之后、QUIC 规则与功能规则之前；EXP-WRTC-02 四组合下位置恒定）。前 5 条为私有地址例外（目标 IP 命中 `private_ip` 规则集 → 直连），后 5 条为拒绝：

| 序 | 规则 | 协议/端口 |
|---|---|---|
| 例外1–5 | `AND,((NETWORK,UDP|TCP),(DST-PORT,端口),(RULE-SET,private_ip,no-resolve)),直连` | UDP 3478 / TCP 3478 / UDP 5349 / TCP 5349 / UDP 19302-19309 |
| 拒绝1–5 | `AND,((NETWORK,UDP|TCP),(DST-PORT,端口)),REJECT` | 同上五组 |

覆盖矩阵（与 §3 对照）：

| 通道 | 是否拦截 | 备注 |
|---|---|---|
| STUN/TURN UDP/TCP 3478、TLS 5349 | ✅ | 双传输均覆盖 |
| Google 系 STUN UDP 19302-19309 | ✅ | **TCP 19302-19309 不拦**（仅 UDP 行）——与 3478/5349 的双传输处理不对称；Google STUN 实践以 UDP 为主，影响小，但属清单事实 |
| TURN over TCP/TLS 443 | ❌ | 代码注释明示刻意放行，避免误伤普通 HTTPS |
| 非标端口 STUN/TURN、媒体面动态端口、应用自带中继 | ❌ | §3 的原理边界，非清单可解 |
| 目标为私有 IP 的同端口流量 | 不拦（例外先行） | 例外按目标 IP 经 private_ip 判定（no-resolve）；域名型内网服务解析到私有 IP 时同样落入例外——此为规则语义推导（E2），运行时未验证（U-W7-2） |

优先级实测：开关2 段恒位于兜底链与功能规则之前，「开关2 优先于开关1」的项目既定决策（2026-10-16）在生成物上的落点是**规则序**（REJECT 先于一切后续匹配命中），而非开关间逻辑——开关1 本身无规则可被优先。

## 6. QUIC 处理现状（定稿）

- **实现形态**：无内核字段，靠单条逻辑规则（`blockForeignQuic`，L172）：`AND,((NETWORK,UDP),(DST-PORT,443),(NOT,((OR,((RULE-SET,cn_additional),(RULE-SET,cn_ip,no-resolve)))))),REJECT`。语义逐步拆解：UDP/443 且目标既不命中 cn_additional 域名集、也不命中 cn_ip 网段 → REJECT。由独立开关「屏蔽国外QUIC」控制，**默认开**（与开关2 的默认关不同）。
- **与规则集的联动（E4，EXP-QUIC-01）**：开关关闭时，该规则消失且 `cn_additional` provider 被一并删除（providers 38→37）——规则与其例外数据源同生同灭，生成物自洽，无悬空引用（EXP-INT-01 亦确认）。
- **与开关2 的边界**：两者端口/协议不重叠（QUIC 仅 UDP/443；STUN 清单无 443 条目，且 TURN/TCP 443 被刻意放行），**无规则冲突面**；叠加顺序上 STUN 段在前、QUIC 在后（实测索引），互不影响命中。
- **不对称发现（E2 规则序推导，待运行时确认 U-W7-3）**：QUIC 规则**没有 private_ip 例外**。UDP/443 指向私有 IP 的流量（如内网 HTTP/3 服务）在规则序上先于兜底的 `RULE-SET,private_ip,直连` 命中本条而被 REJECT；prefixRules 首段的 `RULE-SET,private,直连` 是域名行为集，对 IP 字面目标不构成例外。与开关2 特意设置 5 条私有例外的处理形成对照——同一脚本内两种例外策略并存，推测为迭代时序所致而非有意设计（无注释说明），列 WP-14 用例与 WP-15 决策输入。
- **对自身 DNS 的影响**：脚本 DoH 恒 `prefer-h3:false` 且未用 `#h3` 参数，自身解析不走 UDP/443 的 H3 通道，**不存在底稿曾提示的自伤面**（该风险面只对「客户端/其他应用自设 H3 DoH」成立，与本脚本无关）。
- **影响面（E1 假设，引底稿 §4）**：国外站点/应用的 HTTP/3 被拒后通常回退 TCP/TLS，功能多不中断、失去 H3 时延优势；个别回退不佳实现可能加载异常。逐应用表现未验证。sniffer 在开关开启时含 QUIC 443/8443 嗅探配置（main sniffer 段），与本规则是不同层面（嗅探识别 vs 出口拦截），不冲突。

## 8. 误伤场景与回退方法（定稿版）

- 开关2 误伤通话/会议/游戏语音 → 关开关2（保留开关1）；或对具体内网目标依赖既有私有例外（公网服务无此路径）。逐应用清单待运行时阶段建立，本稿不预断。
- QUIC 拦截导致个别应用加载异常 → 关「屏蔽国外QUIC」（规则与 cn_additional provider 自动一并移除，已实测）；内网 H3 服务受影响的情形见 §6 不对称发现，回退同为关该开关（无更细粒度手段，列 WP-15 输入）。
- dns.ipv6=false 导致只走 AAAA 的局域网服务不可达 → 以 nameserver-policy 为该域名单独指定可解析 v6 的服务器，而非全局翻转（与 WP-6 §4 决策表配套）。
- 开关1 场景下 STUN 仍泄露/失败 → 先查三处：漏网之鱼的用户选择是否为直连、所选组是否只含显式 udp:false 节点、App 层顶层 ipv6 是否为 true（§1.3 三方组合）。
