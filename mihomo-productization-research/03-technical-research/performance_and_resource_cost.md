# WP-11 性能、资源与冷启动研究

- 工作包：WP-11（P2）；执行日期：2026-10-28
- 证据等级：E4（隔离实测）为主；涉及 mihomo 运行时行为处只给测试方案、不给结论
- 原始数据：`01-baseline/_work/wp11_*.json`、`wp11_pooled.json`；实验记录：`07-validation/experiment_log.csv` EXP-906~909；来源登记：`evidence/wp11-sources.csv`（SRC-551~556）

## 0. 结论摘要

1. **脚本生成成本是毫秒级**：五脚本在 25/200/1000 合成节点下 `main()` 生成耗时池化中位数分别为约 1 / 3–5 / 13–24 ms。相对于冷启动中真正的成本项（规则集网络下载、内核加载），脚本生成可忽略——任何"轻量 = 生成更快"的说法在本量级上没有用户可感知差异。
2. **耗时热点单一**：Go 主版管线中 `filterAndNormalizeProxies`（节点过滤/标准化）占 1000 节点总耗时的约 79%，且随节点数近线性增长；代理组与规则构建成本近似常数（与节点规模无关）。未来若做性能优化，只需盯这一阶段。
3. **输出规模由代码常量决定**：规则条数（Go 线 96 / 上游线 57–58）与规则集数（38 / 46–47）在三档规模下完全不变；组数在地区饱和后恒定（45–51）。节点规模只影响输出 JSON 体积（1000 节点约 331–374 KB）与节点标准化耗时。
4. **首启下载量两线同量级**：规则集文件合计 Go 线约 876 KiB（37 个唯一文件）、上游线约 888 KiB（45 个），均为当日快照；脚本本体 gzip 后 14–24 KB。冷启动网络请求数 ≈ 规则集数 + 图标（懒加载） + Geo 数据库（脚本外）。
5. **生成阶段与网络完全解耦（实测）**：五脚本源码无任何网络 API；同输入两次生成输出哈希一致；输入携带不可达 rule-provider 时生成照常成功（3 ms）且不透传该集。规则集不可达的等待与失败只发生在 mihomo **运行时**加载阶段，不归脚本——该部分本环境不可测，方案见 §6。

## 2. 生成耗时基准（EXP-906）

池化中位数（ms，21 样本/格）与极差：

| 脚本 | n=25 中位（极差） | n=200 中位（极差） | n=1000 中位（极差） |
|---|---|---|---|
| Go 主版 | 0.86（0.53–3.61） | 4.59（2.23–31.88） | 17.76（11.60–41.97） |
| Go-smart | 1.02（0.54–3.22） | 4.68（2.28–19.90） | 13.50（10.09–41.99） |
| combo | 1.01（0.55–4.55） | 3.21（2.34–18.40） | 13.15（10.26–16.69） |
| 上游原版 | 1.78（0.56–10.28） | 2.74（2.00–19.99） | 22.00（8.84–80.20） |
| 旧 smart | 0.98（0.54–7.30） | 2.93（2.31–11.81） | 24.22（18.82–231.78） |

判读（重要）：

- **变体间不可排名**。Go 三件套代码近乎同源，中位数却互有高低且轮次间翻转（如 Go 主版单轮在 n=200 曾测得 9.18 ms、池化后 4.59 ms）；极差上限被共享沙箱的调度噪声污染（旧 smart 出现 231.78 ms 的离群样本）。可信结论只有量级：**同规模下五脚本同属一个量级，差异 <2 倍且小于环境噪声**。
- **规模弹性**：25→1000 节点（40 倍），中位数约增长 13–25 倍，呈亚线性至近线性，与 §3 的热点构成一致（常数项 + 线性项混合）。与 WP-9 EXP-903 的独立测量交叉印证（200 节点 3.2–3.6 ms、2000 节点 27.5–32.3 ms，同量级）。
- 客户端外推：手机端 JS 引擎与低端 CPU 可能慢 5–20 倍（未测，量级推测），1000 节点生成仍应在亚秒级，不构成启动瓶颈。

## 3. 阶段分解（EXP-907，Go 主版）

按 `main()` 自身管线顺序逐阶段计时（预热 2 + 计时 7，中位数）：

| 阶段 | n=200 | n=1000 | 随节点数 |
|---|---|---|---|
| filterAndNormalizeProxies（过滤/改名/地区倍率识别） | 2.89 ms | 9.20 ms | 近线性，主导项 |
| buildRegionGroups（地区组三件套） | 0.28 ms | 1.24 ms | 弱增长 |
| buildDnsAndHostsConfig | 0.14 ms | 0.54 ms | 弱增长 |
| buildFunctionalGroups（功能组+规则+providers） | 0.14 ms | 0.23 ms | 近常数 |
| buildCustomizeGroups | 0.01 ms | 0.01 ms | 常数 |
| 管线合计（中位） | 4.87 ms | 11.69 ms | — |

n=1000 时节点标准化约占 79%。该阶段内部为逐节点正则匹配与改名（名称匹配缓存使重复命名近零成本，见 EXP-903/904）。优化方向若有需求：减少逐节点正则条数、预编译匹配表——但以当前量级（千节点 ~9 ms）没有实施必要。

## 5. 静态体积与首启外部资源（EXP-908）

源文件体积：Go 主版 72,297 B（gzip 22,013）、Go-smart 74,075 B（22,705）、combo 78,440 B（23,716）、上游 52,977 B（14,183）、旧 smart 65,173 B（18,721）。脚本经 CDN 分发时按 gzip 量级计均为 14–24 KB，可忽略。

首启需下载（规则集，2026-10-28 以 HEAD Content-Length 实测，AWAvenue .mrs 无长度头、以 GET 实测 8,440 B 补齐）：

| 线 | 规则集数 | 唯一文件 | 已知体积合计 | 备注 |
|---|---|---|---|---|
| Go 线（三件套相同） | 38 | 37 | 897,062 B（≈876 KiB） | 37/37 全部测得 |
| 上游线（原版） | 46 | 45 | 909,317 B（≈888 KiB） | 45/45 全部测得 |

- 首启网络请求数构成：规则集 37–45 次（可并发）+ GeoIP/GeoSite 数据库（客户端/内核管理，不在脚本范围）+ 策略组图标（Go 输出含 32 个唯一图标 URL、上游 37 个，客户端 UI 懒加载、可缓存，不阻塞启动）。
- 两线下载量同量级；Go 线文件数更少但单个 .mrs 较大。规则集内容随上游更新漂移，本节为当日快照（巡检 rules-canary 已在持续探活，可顺带记录体积趋势）。

## 6. 冷启动与失败等待

### 6.1 脚本侧（已实测，EXP-909）

- 五脚本源码 grep 网络 API（`fetch(`、`XMLHttpRequest`、`$httpClient`、`require(`）**零命中**：生成过程没有任何网络调用点。
- 同一夹具两次生成，输出 JSON 的 sha256 完全一致（`49f27b80e3579608`）：输出确定、无随机/时间依赖。
- 输入配置携带指向 `https://10.255.255.1:81/never.mrs`（无路由地址）的 rule-provider 与引用它的规则：生成 3 ms 成功，输出为脚本自建的 38 个规则集（输入 provider 不透传）。
- 结论：**规则集 URL 不可达对生成阶段零影响、零等待**。生成失败模式只有输入结构类（如含 proxy-providers 时脚本按设计抛错终止，属预期行为）。

### 6.2 mihomo 运行时侧（本环境不可测，给方案不给数字）

冷启动总时长 = 客户端启动 + 脚本生成（§2，毫秒级） + 内核解析配置 + 规则集/Geo 首次下载（§5，约 0.9 MB + Geo 数据库） + 规则编译加载。其中运行时部分取决于内核版本、网络与设备，本沙箱无 mihomo 内核与真实客户端，**不提供估算数字**。后续在真实环境（WP-10/WP-14）执行以下方案：

1. **冷启打点**：清除客户端规则集缓存后首启，用客户端日志时间戳（或系统 logcat/Console）测「启动→可代理」时长，同一设备重复 ≥5 次取中位数；分别在 Wi-Fi/移动网络下测。
2. **规则集更新耗时**：手动触发全量更新，记录 38 个集的总耗时与最慢单集；对比 interval 到期自动更新的行为差异。
3. **失败等待**：将某一规则集 URL 改指无路由地址（或断网）后启动，观察内核是阻塞启动、超时降级还是带错启动，记录等待时长与日志——这是"规则集源失效"风险（R-002）的运行时验证。
4. **内存/CPU**：1000 节点配置下记录客户端进程 RSS 与稳态 CPU（Android `dumpsys meminfo` / iOS Instruments），与 25 节点配置对照，分离"节点规模"与"规则规模"的贡献。

## 7. 局限

- 计时在与其他 Agent 共享的 2 vCPU 沙箱中进行，调度噪声显著：极差上限不可信，结论只取中位数量级；变体排名在本数据下不成立。
- Node V8 与客户端 JS 引擎（JavaScriptCore/QuickJS 等）性能特征不同，绝对毫秒值不可迁移到真实设备；可迁移的是量级与构成比。
- 合成夹具的地区/倍率/前缀分布为人工设定；真实订阅的命名多样性可能使名称匹配缓存命中率与本测不同。
- 规则集体积为 2026-10-28 单日快照；运行时内存、冷启动端到端、规则集加载失败等待均未测（方案见 §6.2）。

## 8. 对产品定义的输入（供 WP-5 参考）

- "轻量版"的可测量差异不应设在生成耗时（无感）或脚本体积（KB 级），而应设在**规则集数量与首启下载量、组/规则常量规模**上：当前 Go 线 38 集/96 规则即为全量基线；若做轻量版，砍服务组对应的 providers 是唯一能显著改变首启成本的杠杆。
- 节点规模在现实区间（≤1000）内不构成任何版本的性能约束，不需要按节点数分版。
