# WP-12 供应链审查 — 分发链完整性与信任边界

- 审计日期：2026-10-28（Asia/Taipei）；基线同 `threat_model.md`
- 范围：从作者提交到用户设备生效的完整链路；只读审查，未做任何仓库变更

## 1. 分发链全景

```
作者编辑（本地 phase3 副本）
  │  ① 人工推送：GitHub Contents API 逐文件（铁律：拉最新底板→小步编辑→推后验证）
  ▼
GitHub 仓库 gaomolan/MyClash-Rules @myclash-rules（单一事实源；无 tag/release）
  ├─ ②a raw.githubusercontent.com ── 用户直连导入脚本 / bett-rules 规则面（源站直出）
  ├─ ②b jsDelivr（cdn/fastly 双节点）── 脚本镜像地址 / 自有图标 / Geo 库（第三方缓存 CDN）
  ├─ ②c jsdmirror（国内公益镜像）── 图标基址（上游仓）/ Emby·emos 规则 / 旧线 bett 基址
  ├─ ②d GitHub Actions（sync-myclash.yml）── 每 4h 拉上游 → 拼接 → 自动直推默认分支
  └─ ②e 静态文件站 353355.xyz ── cn-additional-list 单文件直供
  ▼
客户端（Bettbox 等）
  ├─ 脚本执行：每次配置生成时全权改写分流/DNS 面（无沙箱校验、无签名验证）
  ├─ 规则集：按 interval 拉取 .mrs，落盘缓存（无哈希锚定）
  ├─ Geo 库：geo-auto-update 周期更新（无哈希锚定）
  ├─ 图标/UI/模型：按需下载（UI 锚 latest；模型由内核按默认址下载）
  ▼
生效配置（用户流量决策面）
```

## 2. 逐环节篡改面与缓存面

| 环节 | 篡改面 | 缓存面 | 现状评估 |
|---|---|---|---|
| 本地编辑→推送 | 编辑机/账号凭据被盗即全权（与 T-03 同源） | — | 流程铁律健全（拉底板、防整推覆盖），但属自觉纪律，无技术强制（如分支保护状态待确认） |
| GitHub 仓库 | 账号被盗、协作者误推、分支强推改写历史 | GitHub 重定向（改名后旧地址靠重定向续命，旧名被抢注即失效） | 无 tag/release → 无不可变锚点；提交历史可审计是唯一事后手段 |
| raw 直出 | 依赖 GitHub 账号安全，无独立第三方 | raw 本身有短缓存（分钟级） | 全链中信任环节最少的一条；Go 线规则面已迁至此（正确方向） |
| jsDelivr | 第三方 CDN 运营方 + 其 GitHub 拉取链；对超限仓库直接拒绝服务（bett-rules 因包体 >50MB 实测 403——可用性教训而非安全事件，证明「换 CDN」不是免费冗余） | jsDelivr 对分支文件有缓存与 purge 机制；分支更新后存在新旧并存窗口（本项目 2026-10-27 靠手动 purge 收敛） | 适合图标/Geo 等展示与数据面；不适合作为规则面的唯一通道 |
| jsdmirror | 国内公益镜像：运营主体与审计透明度低于商业 CDN；多一层二次分发即多一层内容替换面 | 实测分钟级 403 抖动（可用性）；缓存策略不透明 | 现行仍承载：图标基址（全线）、Emby/emos 规则（全线）、bett 基址（custom/旧 smart 两线）——**规则面经此镜像的两条旧线是当前最大的「已知且可消除」的供应链敞口** |
| 353355.xyz 静态站 | 个人域名单站：无仓库、无版本史、无第三方见证，内容可变而 URL 不变 | 未知 | DEP-009：全清单出处最不透明的依赖；名单规模小，内联或迁仓的成本最低 |
| GitHub Actions（sync） | 见 §3 专节 | Actions 缓存不涉及内容面 | 自动通道与人工通道的门禁标准不一致（见 §3） |
| 客户端拉取与缓存 | 本地网络劫持（HTTPS 已大幅压缩此面；明文 DNS 并列项是残余，见 T-05） | 规则集落盘缓存使「一次投毒、长期有效」成为可能：投毒内容的存活期 = 缓存有效期与 interval 的叠加，而非单次请求 | 客户端无内容校验是生态级限制，非本项目可独力改变；项目侧能做的是让源头可信度与巡检指纹兜底 |

**完整性结论**：链上不存在任何一处「内容指纹比对」。所有信任都锚在「账号没被盗 + CDN 没作恶/没出错」上。这在同类社区脚本项目中是普遍状态，但本项目既已在做 rules-canary 巡检，把巡检从「探活」升级为「验指纹」是全链性价比最高的完整性补强（覆盖 T-01/T-02，且能顺带发现 CDN 缓存污染）。

## 3. sync 自动同步的信任边界（专节）

sync-myclash.yml（SRC-002 全文直读）的信任结构：

```
上游 AIsouler/MyClash@main（外部信任根，浮动）
   │ curl 拉取（HTTPS；无 hash 校验——且上游不提供可校验锚点）
   ▼
拼接：上游全文 + 自有 customPatch.js（字节级确定性，WP-1 已验证）
   │ Validate：仅查 ① customPatch 标志串存在 ② 上游含 function main(config)
   ▼
github-actions[bot] 提交并直推默认分支（自动，无人工审核点）
   ▼
主力机订阅 URL 自动刷新 → 用户设备生效
```

**安全含义（WP-1 发现的延伸）**：
1. **信任根外置**：custom 线的实际内容控制权在上游维护者与上游账号安全上，不在本项目手里。本项目对它的全部审查手段是事后的（人工精选政策管不到这条线）。
2. **隐式耦合放大故障半径**：customPatch 引用的 4 个上游内部标识符（SRC-107）属于上游的「非公开 API」——上游任何重构都是对本项目的破坏性变更，而 Validate 的两项检查恰好都不覆盖它们。**校验与耦合错位**是这条链上最具体的可修复缺陷：补 4 条 grep 断言即可把一类静默失效变成流水线红灯。
3. **自动发布无差异门禁**：sync 对「上游这次改了什么」不做任何差异审阅即全量下发到在用设备。与人工线「拉底板→小步编辑→diff 自查→推后验证」的铁律相比，自动线的门禁标准明显更低，而它服务的恰是主力机。门禁标准与设备重要性倒挂。
4. **可回溯性尚可**：sync 提交信息含上游提交标题（中文化后），但未见上游 commit hash 记录；出问题时定位「哪一版上游引入」需要另行比对。建议在提交信息或拼接文件头中写入上游 hash（拼接产物头部已有订阅地址行，加一行上游 hash 注释成本极低）。

**处置选项**（供 WP-15 决策，本 WP 只给安全排序）：A. 最小修复：Validate 加标识符断言 + 生成后冒烟 + 记录上游 hash（保留自动性，堵住静默失效）；B. 中度：sync 只生成候选提交/分支，人工确认后合并（恢复门禁一致性）；C. 彻底：随双仓迁移取消自动 sync，custom 线并入精选制（消除外置信任根，但增加人工频率成本）。

## 4. 自有资产托管与可见性切换（与 R-004 联动）

自有图标（Claude/GitHub/Cloudflare-v2/Cloudflare 四件，DEP-016…019）经 jsDelivr 锚定自有仓浮动分支。仓库由公开转私有的动作对它们的影响链：raw 与 jsDelivr 的匿名拉取同时失效 → 已导入设备图标空白（功能无损、fail-soft），且 jsDelivr 历史缓存何时彻底失效不可控（不可作为过渡依赖）。因此 R-004 的处置顺序在供应链视角再次确认：**先在公开仓落图标资产 → 脚本引用改指新址并推送 → 实测拉取正常 → 最后才切换旧仓可见性**。顺序颠倒（先转私有）会造成一段图标全灭的窗口，且回滚（重新公开）与项目意图相悖。

另注意三件套内部图标引用不一致（Go-smart 用 `Cloudflare.svg`、主版/combo 用 `Cloudflare-v2.svg`），迁移时应统一为单一命名，避免新仓出现双份同义资产。

## 5. 发布前建议清单（供未来公开发布执行，本阶段不执行）

**硬门禁（不满足不发布）**
1. combo 脚本不进入公开仓候选集；候选集逐文件过敏感形态扫描（与 `secret_handling_review.md` 同口径）并留扫描记录。
2. 自有图标已迁入公开仓且脚本引用已切换、实测可匿名拉取（在旧仓转私有之前完成）。
3. 公开仓候选脚本的全部外部 URL 已逐项登记（复用 DEP 清单口径），无未登记的个人域名依赖（DEP-009 须已处置：内联或迁入可审计仓库）。
4. sync 通道已按 §3 选项之一处置，或明确标注 custom 线不在公开发布范围。

**版本与回滚**
5. 首发打语义版本 tag，脚本头版本号与 tag 一致；文件头同时给出浮动链接（尝鲜）与固定 tag 链接（稳定）。
6. 保留上一版本脚本副本于公开仓可达路径，回滚动作 = 用户改订阅链接或维护者回退默认分支一提交。
7. 每次发布在仓内 CHANGELOG 记录：变更摘要、涉及的规则源/图标变更、上游 hash（若含 sync 内容）。

**完整性与巡检**
8. rules-canary 增加内容指纹基线（关键 .mrs 与 Geo 文件 sha256 清单 + diff 告警），指纹清单本身随仓库版本管理。
9. 巡检覆盖全部在用分发通道（含 jsdmirror 上的图标/Emby 面），而非只测主源。

**文档与信任契约**
10. README 设「信任与接管面」一节：脚本会改写哪些字段、DNS 归脚本、规则来自哪些第三方源、健康检查与 Geo 的来源——把 T-05/T-10 的隐性边界显性化。
11. 删除或标注旧 smart 注释中的 gh-proxy 镜像示例（DEP-028）；GBM 模型给出官方原址与手动放置说明。
12. external-ui-url 改锚固定 release tag 或移除预置（DEP-026）。

## 6. 限制

- 分支保护的实际开启状态、仓库协作者与 Actions 权限明细未在本 WP 核验（需仓库设置面证据，列为待确认项）。
- 客户端（Bettbox 等）对规则集缓存的精确失效语义以 WP-10 的客户端研究为准；本文件的 fail-stale 判断基于 mihomo 通行行为与 WP-1 记录，未做真机复测（E5 缺失，与全项目状态一致）。
